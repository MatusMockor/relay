# Relay - architecture

AI-native mail client in the spirit of Superhuman. Desktop app for macOS and Linux, optional sync server, AI that runs either on the server or locally on the user's machine through the user's own Claude Code / Codex CLI subscription.

## Product modes

| Mode       | Who uses it     | Where data lives                                          | Mail sync                                     | AI                                        |
| ---------- | --------------- | --------------------------------------------------------- | --------------------------------------------- | ----------------------------------------- |
| **Local**  | no registration | SQLite on the device                                      | desktop main process talks IMAP/SMTP directly | local CLI only                            |
| **Synced** | registered user | Postgres on the server, local SQLite cache on each device | server syncs 24/7 (IMAP IDLE)                 | server worker or local CLI (user setting) |

- The user picks the mode on first launch: "Pokračovať bez účtu" (local) or "Pripojiť k serveru" (server URL + register/login).
- The server URL is a per-device setting and can be changed in Settings → Server. Multiple saved servers are allowed.
- In synced mode everything except device-only preferences (window size, panel widths, selected account, server URL) is stored on the server and pushed to all signed-in devices in real time.
- The server is multi-user from day one: every row is owned by a `userId`. Today it runs on the owner's Linux box, later anyone can self-host it.

## High-level diagram

```
apps/desktop (Electron)
  renderer (React)  ── MailClient interface ──┬── RemoteMailClient ── HTTPS + WebSocket ──► apps/server (NestJS)
                                              └── LocalMailClient  ── IPC ──► main process
  main process: LocalEngine = @relay/engine + @relay/store-sqlite + @relay/mail-core + @relay/ai (local runner)

apps/server (NestJS, Docker Compose on the owner's Linux, optional Cloudflare Tunnel)
  auth/devices · mail accounts · sync scheduler (pg-boss) · REST API · WS gateway · AI worker
  = @relay/engine + Postgres repositories + @relay/mail-core + @relay/ai (server runner) + @relay/mcp-mail (HTTP)
```

## Monorepo layout

```
apps/
  desktop/        Electron app: main, preload, renderer (React)
  server/         NestJS API + workers
packages/
  shared/         domain types, zod schemas, API contract, WS events (no runtime deps besides zod)
  engine/         application services + repository/provider PORTS (interfaces); pure TS, no I/O
  store-sqlite/   SQLite (better-sqlite3 + Drizzle) implementations of engine repository ports
  mail-core/      MailProvider adapters (IMAP via imapflow, Gmail via XOAUTH2), SMTP sender, MIME parsing, threading, Jira classifier
  ai/             AiRunner port + Claude Code / Codex CLI runners, CLI detection, prompts, output parsing
  mcp-mail/       MCP server exposing mail tools backed by engine ports (stdio + streamable HTTP)
  ui/             design tokens and React components (ported from the approved prototype)
  config/         shared tsconfig / eslint / prettier / vitest presets
```

Dependency rule (enforced by ESLint import boundaries):

```
shared  ◄── engine ◄── store-sqlite
   ▲           ▲  ◄── mail-core (implements engine MailProvider/MailSender ports)
   │           ▲  ◄── ai        (implements engine AiRunner port)
   │           ▲  ◄── mcp-mail
   ├── ui
   └── apps/* may depend on any package; packages never depend on apps
```

`engine` depends only on `shared`. Everything with I/O lives outside `engine` and is injected.

## Hexagonal core (`@relay/engine`)

- **Ports** (interfaces, one per file) in `engine/src/ports/`:
  - repositories: `AccountRepository`, `MailboxRepository`, `MessageRepository`, `ThreadRepository` (folder-view query with cursor pagination, unified or per account), `LabelRepository`, `SplitRepository`, `AutomationRepository`, `AutomationRunRepository`, `TaskRepository`, `ReminderRepository`, `DraftRepository`, `ScheduledSendRepository`, `SettingsRepository`, `AiResultRepository`, `AiJobRepository`, `SyncStateRepository` (UIDVALIDITY / last UID / HIGHESTMODSEQ / frozen initial-sync window per mailbox), `MessageBodyRepairRepository` (optional, desktop only: stored messages whose bodies contain U+FFFD and a body-only update). User-facing methods take the `UserId` first; sync-internal methods are keyed by account or mailbox.
  - `UnitOfWork.run(work)` passes transaction-bound `Repositories` to `work`.
  - mail: `MailProvider`, `MailProviderFactory`, `MailSender`, `UnsubscribeSender` (RFC 8058 one-click POST), `CredentialVault`, `AttachmentStore`, `MessageParser`, `ThreadResolver`, `JiraClassifier`, `SplitMatcher`, `AutomationMatcher`.
  - AI: `AiRunner` (`run(request): AsyncIterable<AiEvent>`), `AiRunnerRegistry`.
  - infrastructure: `EventPublisher`, `Clock`, `IdGenerator`, `Logger`.
- Engine-internal types (raw/parsed messages, sync cursors, pages, AI requests) live in `engine/src/model/`. They never cross the wire.
- `PORT_TOKENS` (`engine/src/tokens.ts`) gives every port a `Symbol.for('relay.engine.<Port>')` token, used by Nest providers and the desktop composition root.
- `EngineError` subclasses (`NotFoundError`, `ValidationError`, `ConflictError`, `ForbiddenError`, `ProviderError`, `NotImplementedError`) carry an `ApiErrorCode`; HTTP and IPC adapters map them to the shared error shape.
- **Application services** in `engine/src/services/`, one use case family per file: `SyncService`, `InboxQueryService`, `ThreadQueryService`, `MessageActionsService` (done, undo, trash, restore, report spam / not spam, move to a folder and undo the move, read/unread, label, pin), `LabelService` (create, rename, recolour and delete labels), `ReminderService`, `ComposeService`, `TaskService`, `SplitService`, `AutomationService`, `AiService`, `FolderService` (creates, renames, moves and deletes custom folders and Gmail labels on the mail server), `UnsubscribeService` (parses the stored `List-Unsubscribe` / `List-Unsubscribe-Post` headers into https or mailto options and sends one-click unsubscribes).
- All database access goes through repository ports. No service, controller or IPC handler talks to Drizzle directly.
- Server implements the ports with Postgres + Drizzle; local mode implements them with SQLite + Drizzle (`store-sqlite`). The same services run in both places.

## Domain model (see `packages/shared/src/domain`)

`User`, `Device`, `MailAccount` (provider: `imap` | `gmail` | `outlook`, color, isPrimary, sync interval, status), `ImapSmtpSettings`, `AccountCredentials` (password or OAuth tokens, never sent to clients), `Mailbox` (role: inbox, sent, drafts, trash, archive, spam, custom, label, system; `subscribed`, `uidValidity`), `Message`, `ThreadSummary` / `ThreadDetail`, `ThreadAction`, `Label` (`kind`: `keyword` for IMAP keywords or `gmail` for Gmail labels, `remoteName` is the keyword or the Gmail label path), `Split` (rule-based view of the inbox), `Automation` (rule that runs actions on new mail), `Task` (one per Jira issue or created by AI), `Reminder`, `Draft`, `ScheduledSend`, `AiJob` / `AiResult` / `AiEvent`, `UserSettings` (synced), `DeviceSettings` (device-only), `FolderView`.

- Ids are branded strings (`UserId`, `ThreadId`, ...) and timestamps are ISO 8601 strings with offset, so the same types work over HTTP, WebSocket and IPC.
- A `Split` matches a message when any of its rules matches. `accountId: null` means the split applies to the unified inbox. An `exclusive` split removes matching threads from the main inbox. A `hideTasks` split leaves out threads that are in Úlohy (have a task that is not done).
- An `Automation` runs when all of its conditions match a new inbox message (split rule conditions, the Jira event kind, a recipient address or domain in To / Cc, and "has a file attachment"). Actions are objects discriminated by `type`: AI summary, AI-judged task, notification, mark read, pin (IMAP `\Flagged`), archive, `addLabel {labelId}` and `moveTo {mailboxId}`. A rule holds each simple action and each label at most once, at most one `moveTo`, and never `moveTo` together with `archive`; inputs still accept the legacy string actions (`'task'`), and data migrations (SQLite `0024`, Postgres `0026`) rewrote stored string arrays to objects. The runner executes actions in the fixed order notify, summary, task, markRead, pin, addLabel, moveTo, archive, so flags and labels are written before the move changes locations; `moveTo` goes through `MessageActionsService` `move` for the whole thread (a real IMAP MOVE, or label plus archive for a Gmail `label` mailbox) and `addLabel` through `addLabel`. A failing action, such as a target folder or label deleted after the rule was saved, is logged and the remaining actions still run; the client marks such tokens as "Priečinok už neexistuje" / "Štítok už neexistuje" by comparing the targets with the account's mailboxes and labels. `moveTo` and `addLabel` need an account scoped rule: `AutomationService` rejects them on a rule for all accounts and validates that a newly added target belongs to the rule's account and that a move target has role `custom`, `label`, `inbox` or `archive` (targets already stored on that rule are not re-validated, so a rule whose folder disappeared can still be edited). Automation moves leave the usual `move-origin` records; they are per thread and expire after the 1 hour undo window, so they only let the user undo that thread's move and never affect other threads. "Použiť aj na existujúce" (`AutomationService.applyToExisting`, `POST /automations/:id/apply`, IPC `local.automations.apply`) reads the newest 500 inbox threads of each of the rule's accounts with their messages' match subjects through `AutomationCandidateRepository` (served by the existing account/state/last-message indexes), matches each message against the rule and keeps the newest 500 matching threads. Jira conditions use the real per-message classification, recomputed from the stored message with the same `JiraClassifier` the ingestor uses, never an invented event kind. Only the mail actions (mark read, pin, label, move, archive) run. Applies are serialized per rule in process; each thread is re-read and skipped unless it is still in the inbox, and it is gated by claiming its newest matching message in `AutomationRunRepository` (the other matching messages are claimed too), so concurrent or repeated applies never run a thread twice. When an action fails, the thread counts as `failed` and its claims are released so a later apply retries it; mail actions are idempotent, so the actions that already succeeded are harmless to repeat. The result is `{matched, applied, failed}`. Each rule picks its AI runner, a model and effort from the static catalog in `shared/src/domain/ai-model-catalog.ts`, and optional instructions. Rules never run on the initial sync backlog, and `AutomationRunRepository` records each automation and message pair so a rule fires at most once per message. The seeded `Jira tasky` preset starts turned off; once the user turns it on it keeps the classic Jira task behavior (create or reopen by Jira key without AI) until the user adds instructions or turns it off again. Presets already stored keep their `enabled` value, and without a stored preset no Jira task is created. Like any other rule it can be renamed, scoped to one account, edited or removed. Removing it records the preset in `removed_automation_presets` (SQLite `0026`, Postgres `0028`) through `AutomationRepository.markPresetRemoved`, so `AutomationService` never seeds it again; "Obnoviť predvolené Jira pravidlo" (`AutomationService.restoreDefault`, `POST /automations/restore-default`, IPC `local.automations.restoreDefault`) clears that record and seeds it again, turned off. Which Jira event kinds create or reopen such a task is the user setting `jira.taskEvents` (default `mention` and `assigned`); other kinds create nothing and leave an existing task untouched.

"Done" = archive (IMAP move to archive mailbox / Gmail remove INBOX label). Read state, done, trash, spam and labels are mirrored back to the mail provider so other clients see them too.

- Sync covers the mailbox roles inbox, sent, archive, trash, spam and custom (`DEFAULT_SYNC_OPTIONS.mailboxRoles`). A missing archive, sent, trash, drafts or spam (`Junk`) mailbox is created on first use (`RoleMailboxEnsurer`).
- Custom folders (`custom`, plain IMAP) are synced when subscribed, or all of them when the server reports no subscriptions at all. The first pass takes the newest `initialFolderMessageLimit` (200) messages regardless of age. Mail that lives only in a custom folder is `done`; custom folders create no Jira tasks, calendar invitations or inbox arrivals. A mailbox whose UIDNEXT, message count and HIGHESTMODSEQ did not change since the last complete pass is skipped.
- Gmail (detected by the `X-GM-EXT-1` capability) is modelled as labels, not folders: every non-special mailbox gets the role `label` and is never synced. Each `label` mailbox has one `Label` with `kind: 'gmail'`, kept in step by `GmailLabelCatalog` during the mailbox refresh, and message membership comes from `X-GM-LABELS` on the copies Relay already syncs (INBOX, All Mail, Sent, Spam, Trash). When labels are added, the synced copies are rescanned for labels. `\Flagged`, `\Important` and other virtual folders get the role `system` and are neither synced nor shown. Plain IMAP labels are keywords (`kind: 'keyword'`); `Junk`, `NonJunk`, `NotJunk` and `$`-prefixed keywords are ignored.
- The mailbox refresher detects remote renames: a vanished mailbox and a new one with the same UIDVALIDITY and message count (one candidate only) are treated as one mailbox, so its id, messages, sync state and Gmail label survive. Anything ambiguous is forgotten and downloaded again. Refreshes that change the mailbox list or labels emit `mailboxes.updated` and `labels.updated`.
- `ThreadState` is `inbox`, `done`, `trash`, `spam` or `reminder`. Trash and spam are holding states: a thread whose mail (ignoring Sent copies) sits only in that mailbox gets that state (spam when it is split between Spam and Trash), and it leaves it once its mail is elsewhere. Generic actions like done refuse a held thread; restore or not spam brings it back.
- Folder views (`FolderView`): `inbox`, `tasks`, `reminders`, `done`, `sent`, `drafts`, `scheduled`, `spam`, `trash`, `mailbox` (threads with a message in `mailboxId`) and `label` (threads carrying `labelId`, in any state except trash and spam). `spam` and `trash` show threads in that state; every other view leaves them out.
- Thread list search and filters (`ThreadListQuery` -> `ThreadFolderQuery`): `q` matches word prefixes of subject, sender, snippet and text body; every term must match. `searchField` (`from` or `subject`) limits the terms to the sender or the subject (SQLite FTS5 column filters on `sender` / `subject`; Postgres tsquery weights `A` subject and `B` sender, where `B` also covers the To and Cc addresses, so `from` on the server matches recipients too). `unread` keeps unread threads, `hasAttachment` keeps threads with a non-inline attachment on a message that matched the search (any message without `q`). `everywhere` replaces the view, split, label and mailbox scope with every state except trash and spam; the account scope stays. The booleans arrive as `true` / `false` query string values. `searchField` without `q` has no effect.
- "Report spam" moves the received (inbox, archive and custom folder) mail of a thread to the spam mailbox and remembers where each message came from, including the exact custom folder; "Not spam" moves it back there (inbox when unknown or when the folder no longer exists). Trash remembers origins the same way, so a trashed spam thread is restored to spam and trashed folder mail returns to its folder.
- "Move to" (`{ type: 'move', mailboxId }`) takes the inbox, the archive, a custom folder (plain IMAP) or a Gmail `label` mailbox. On plain IMAP the received copies (inbox, archive, custom, spam and trash, never Sent) that are not already there are moved with IMAP MOVE; the thread becomes `inbox` when the target is the inbox and `done` otherwise, so a held thread leaves trash or spam and its trash and spam origins are forgotten. On Gmail it is Gmail's own "Move to": the label is added to every local copy and written once per physical message through `X-GM-LABELS` (`MailProvider.setLabels`, preferring the All Mail copy), then the inbox, spam and trash copies move to All Mail and the thread becomes `done`. Moving to where the thread already is changes nothing. Gmail move sources and label ownership are decided per physical message (email id, Message-ID when it is missing), so a label any copy already had is never removed by undo. Each move records a `move-origin` per moved or newly labelled message (its previous mailbox, the Gmail label it added and the trash and spam origins it displaced); `{ type: 'undoMove' }` returns those messages to their previous mailboxes (inbox when that folder is gone), puts the displaced trash or spam origins back and removes the added label. Writing a Gmail label op drops a queued op for the same label on another copy of the same message. A new move of the thread replaces its records, and records older than the one-hour undo window are dropped before every move and undo.
- When a move's COPYUID points at a row Relay already stores in the target (Gmail returns the existing All Mail UID on archive), or on Gmail without a returned UID a row with the same email id is already there, the replayer deletes the moving row instead of moving it, carries its trash, spam and move origins and reply drafts over to the surviving row and journals a thread refresh. A later draft save that still names the deleted row keeps the stored reply reference.
- Labels (Štítky) are managed by `LabelService` (`POST /labels`, `PATCH /labels/:id`, `DELETE /labels/:id`, IPC `local.labels.*`). Names are trimmed, 1-100 characters and unique per account ignoring case (both stores keep a `name_key` column, NFC plus Slovak lower case, with a unique index, and a clash becomes `ConflictError` "Štítok s týmto názvom už existuje."; the key is recomputed only when the name changes, and after the migrations each store rewrites keys that differ from that normalization, giving older labels that collide ignoring case a `\u0001` + id suffix); Gmail names may not start with `[Gmail]` or contain `\`. Colours are Relay-only. Every change emits `labels.updated` (Gmail changes also `mailboxes.updated`).
  - Keyword labels (plain IMAP): creating one stores only the local row (IMAP has no keyword list). `remoteName` is the exact keyword on the server and never changes, so a rename only changes the display name, and adds, removes and purges always write the stored `remoteName`. A new label gets its keyword from `services/labels/keyword-codec.ts`: a name that is a plain IMAP atom without `&` stays as it is, anything else (including every `&`) is encoded as `&` + lowercase hex of the UTF-8 bytes + `-` per run ("Faktúry" becomes `Fakt&c3ba-ry`), which survives servers that fold case. Adopted server keywords are decoded only for the display name, and foreign keywords that are not such encodings are shown as they are. Keywords are compared ignoring case. Names the server reserves (`$...`, `Junk`, `NonJunk`, `NotJunk`) cannot be created. A new keyword may be at most 50 characters after encoding (Dovecot's default `mail_max_keyword_length`), otherwise creation fails with "Názov štítka je pre server príliš dlhý."; renaming changes only the display name and is not limited by it. A server whose `PERMANENTFLAGS` lack `\*` rejects new keywords with `ProviderError` "Server nepodporuje vlastné štítky". Deleting a label removes the row, refreshes its threads and queues a `keyword-purge` that runs `UID STORE 1:* -FLAGS` on every synced mailbox (right away, otherwise on the next sync). The purge record stays as a tombstone until a sync that started after the purge has completed, and while it exists sync never recreates a label from that keyword. A server keyword whose name is already taken by a renamed label is adopted with a numbered name.
  - Gmail labels: create, rename and delete go to Gmail first (`MailProvider.createMailbox`, `renameMailbox`, `deleteMailbox`) and then update the `label` mailbox row and the Label; a rename moves nested labels (`Projekty/...`) with it, keeps their ids and retargets queued `X-GM-LABELS` writes for the renamed tree in the same transaction, a delete keeps the mail in All Mail and clears the label from local threads. Adding or removing a Gmail label on a thread changes every local copy and writes `X-GM-LABELS` once per physical message, preferring the All Mail copy.
- Folder management (`FolderService`, `POST /accounts/:id/mailboxes`, `PATCH /mailboxes/:id`, `DELETE /mailboxes/:id`, IPC `local.mailboxes.*`) changes only `custom` mailboxes (plain IMAP) and `label` mailboxes (Gmail). INBOX, every role mailbox, `system` mailboxes and the `[Gmail]` tree are refused with `ForbiddenError`. Names are trimmed and must not contain the hierarchy delimiter, `*` or `%`, must not be INBOX and must not clash with a sibling (ignoring case). The operations run online against the mail server and are never queued; without a connection they fail with `ProviderError`. Rename and move are one IMAP RENAME (the new path and its subscribed subfolders are subscribed, the old paths unsubscribed), then `relocateTree` moves the stored mailbox and every descendant path, so mailbox ids, messages, sync state, automation `moveTo` targets and the sidebar selection survive; for Gmail the same transaction runs the label service's `relocateLabelTree`, so the matching `gmail` Labels keep their ids and queued `X-GM-LABELS` writes are retargeted. Renaming, moving or deleting a folder is also refused when a stored or listed mailbox inside it is protected. Deleting a plain IMAP folder is refused while it has subfolders (stored or listed). Otherwise, within one connection, every message the server lists in the folder (not only the cached ones) is moved to Trash, for at most three rounds; cached copies keep their rows and get trash origins (restore goes to the inbox once the folder is gone), but only when the stored UIDVALIDITY of the folder (and of Trash, once Trash has been synced) still matches the server, otherwise the move is server-side only and the next sync rebuilds Trash. DELETE is sent only right after STATUS reports 0 messages and a fresh UID search (`listUids(path, { fresh: true })`: NOOP plus an unconditional `UID SEARCH ALL`) of the selected folder is empty. Threads whose mail was already moved are refreshed even when a later step fails. A failed, partial or ambiguous move, or mail that keeps arriving, aborts and keeps the folder; mail already moved stays in Trash. The only remaining gap is mail delivered in the single round trip between that last check and DELETE, which IMAP gives no way to close. After the DELETE the folder is forgotten. Deleting a Gmail label deletes only the label: the mail stays in All Mail, and the label service's `LabelRemoval` drops queued writes for it, removes the Label and its mailbox row and refreshes the affected threads. Each change emits `mailboxes.updated`, and `labels.updated` for Gmail.
- A copy ingested from the spam mailbox never counts as an inbox arrival, so it triggers no automations, AI one-liners or notifications, and it creates no Jira tasks or calendar invitations. An INBOX copy of the same message is classified on its own.

## Server (`apps/server`)

- NestJS 11 with the Fastify adapter, modules per bounded context: `auth`, `devices`, `accounts`, `sync`, `mail` (threads/messages/actions), `tasks`, `settings`, `ai`, `realtime`, `health`.
- Postgres 17 + Drizzle ORM, migrations with drizzle-kit. Repositories implement engine ports; Nest providers bind port tokens to implementations (dependency inversion).
- Jobs: pg-boss (sync per account, reminders, scheduled sends, AI jobs). No Redis.
- Auth: email + password (argon2id), optional TOTP later. Access JWT (15 min) + rotating refresh token bound to a `Device`. Devices can be listed and revoked.
- Mail credentials encrypted at rest (AES-256-GCM, key from `CREDENTIALS_ENCRYPTION_KEY`).
- Realtime: WebSocket gateway on `/realtime`. The client sends `hello` (`apiVersion`, access token) first; the server answers `welcome` and then pushes `event` messages carrying a `RealtimeEvent`: `thread.upserted`, `thread.removed`, `message.upserted`, `task.upserted`, `account.status`, `account.upserted`, `account.removed`, `draft.upserted`, `draft.removed`, `scheduledSend.upserted`, `splits.updated`, `automations.updated`, `automation.notified`, `ai.job.updated`, `settings.updated`, `sync.progress`, `mailboxes.updated`, `labels.updated` (`shared/src/realtime`).
- API contract lives in `shared/src/api`: every endpoint is `{ method, path, auth, params?, query?, body?, response }` built from zod schemas and grouped by area in `api`. The server validates requests with `parseEndpointRequest`; clients build URLs with `buildUrl` and are typed by `EndpointRequest` / `EndpointResponse`. Errors use `{ error: { code, message, issues? } }` (`ApiErrorCode` -> HTTP status in `API_ERROR_HTTP_STATUS`), lists use cursor pagination (`{ items, nextCursor }`).
- Dev runtime: `vite-node` with SWC (decorator metadata) runs `src/main.ts` directly from TypeScript, the same pipeline Vitest uses. A production bundle is still to be decided.
- Deploy: `docker compose up` (server + postgres). Optional Cloudflare Tunnel for remote HTTPS access without open ports. Cloudflare Access is not used because the app has its own login.

## Desktop (`apps/desktop`)

- Electron + electron-vite + React 19 + TanStack Query + Zustand. Same look on macOS and Linux.
- `renderer` only knows the `MailClient` interface (`apps/desktop/src/renderer/data/MailClient.ts`). `RemoteMailClient` uses HTTP + WS, and `LocalMailClient` uses typed IPC to the main process.
- IPC contract lives in `shared/src/ipc`: a channel map of zod schemas (`app.*`, `settings.device.*`, `secure.*`, `ai.*`, `local.*`). The preload exposes `window.relay: RelayBridge` with `invoke(channel, input)` (one Electron channel `relay:invoke`, returns `IpcResult`) and `subscribe(channel, handlers, input)` for streams (`ai.run`, `local.events`). Main validates input and output of every call (`IpcInvokeRouter`, `IpcStreamRouter`).
- Context menus: right-clicking a thread row or a sidebar folder sends the menu items over IPC `app.contextMenu.show`; the main process opens a native `Menu` at the cursor and answers the chosen id or `null`. Without `window.relay` the same request renders as a `Popover` at the click point. "Označiť všetko ako prečítané" calls `FolderReadService.markAllRead` (`POST /threads/mark-read`, IPC `local.threads.markFolderRead`) with the folder scope (any view except `drafts` and `scheduled`): it pages through the folder and marks the unread threads read in chunks of `folderReadPageSize`, each chunk with one unit of work, one `\Seen` mirror and its events, adjusts the mailbox `unreadCount` and returns `{ count }`. Sync keeps a local flag while a provider op for it is still pending.
- Navigation history (`renderer/src/features/history`): a `HistoryRecorder` observes the UI store and keeps browser-like back and forward stacks (at most 50 entries) of locations: account scope, folder, open thread, open search (not the query) and the Settings section with its sub-view (`adding` for Účty, list / templates / rule detail for Automatizácie). Mouse buttons 3 and 4 (window and HTML mail iframes), `app-command` `browser-backward` / `browser-forward` (menu commands `navigate-back` / `navigate-forward`, a pointer and command pair of one press counts once) and Cmd/Ctrl+[ / ] step through it after blurring the focused field (so blur commits run) and running the back guards. Automatic corrections (an unknown account scope falling back to all accounts, the restored stored scope, a draft rule getting its id, a missing open thread falling back to the list) replace history entries quietly instead of recording a navigation. History is one timeline of entries (back, current, forward), and an entry can carry a tag. A thread opened from a notification is recorded as two entries, the list of its placement and the open thread. For a thread not loaded yet both entries are tagged, and when its summary arrives the tagged entries are rewritten to the real placement wherever they are in the timeline; an entry that becomes equal to its predecessor is merged, and the live UI changes only when the current entry was rewritten. Settings never block it; any other overlay or an extra layer above Settings does. Escape keeps its close/up behaviour and is not history.
- `pnpm --filter @relay/desktop dev:web` serves the renderer alone on port 5173. `window.relay` is then absent and the renderer must handle it.
- Windows run with `contextIsolation`, `sandbox` and no Node integration; the preload is bundled as CommonJS. CSP is injected into the built `index.html`.
- `main` hosts the `LocalEngine` for local mode, secure storage (Electron `safeStorage`) for tokens and local credentials, the local AI runner, and native features (tray, notifications, global shortcuts) and auto-update (`electron-updater` behind the `AppUpdater` port, packaged macOS and AppImage only, see `docs/operations/release.md`).
- HTML mail is rendered in a sandboxed iframe (no scripts, remote images blocked by default).
- The main process is bundled as ESM with the workspace packages and their CommonJS dependencies inlined. Every main chunk starts with electron-vite's own CommonJS shim (`require` via `createRequire`, `__filename`, `__dirname`, `main-chunk-banner.ts`), because electron-vite inserts that shim after the last line that looks like an `import`, which in this bundle is inside a JSDoc comment. Without it a bundled `require('stream')` (iconv-lite) fails silently and mailparser stops decoding non-UTF-8 charsets.
- Messages stored by builds with that bug have U+FFFD in their bodies. SQLite migration `0027` queues one `body-repair` pending work per mailbox holding such mail, and the `MessageBodyRepair` sync backfill refetches those messages (at most 50 per sync, resumable by UID), re-parses them and rewrites only text, HTML and snippet (the FTS triggers follow). The thread refresh is journaled before the body is rewritten, so a crash in between never leaves a repaired message with a stale thread. A mailbox whose current UIDVALIDITY differs from its stored sync state (or has none) is dropped from the repair. A message without a stored Message-ID, one that is gone, or one whose Message-ID no longer matches is skipped; a failed fetch skips that message and ends the batch. Postgres is not affected because the server runs mailparser unbundled.
- UI follows the approved prototype `design/prototype/app-a.html` (dark tokens, Inter + JetBrains Mono, split inbox, folder sidebar, right panel with Kontakt / AI / Kalendár, resizable panels, multiple accounts, command palette, keyboard-first).

## AI (`@relay/ai`)

- `AiRunner` port: `run(request: AiRequest): AsyncIterable<AiEvent>` (`AiEvent` is defined in `shared` so it can be streamed over IPC unchanged). Implementations: `ClaudeCodeRunner` (`claude -p --output-format stream-json`) and `CodexRunner` (`codex exec --json`), each spawning the CLI with a mail MCP server attached.
- Runner location is a user setting: `server` (server AI worker uses the CLIs installed on the server) or `local` (the desktop main process uses the CLIs installed on this machine). Like T3 Code environments.
- `CliDetector` reports which CLIs are installed and logged in on the current machine, shown in Settings → AI.
- Tasks: one-line summary, thread summary + checklist, reply suggestions, rewrite draft, free-form chat over mail, create task from mail, automation task verdict (`automationTask`). Jobs can carry a per-job model and effort that the CLI dialects pass on (`--model`, Claude `--effort`, Codex `-c model_reasoning_effort`).
- Safety: the agent gets read-only mail tools plus `create_task`/`create_draft`. Sending always needs explicit user confirmation in the UI. Email content is untrusted input (prompt injection).

## Mail providers (`@relay/mail-core`)

- `ImapMailProvider` (imapflow): folders (list, create, rename, delete), incremental fetch by UID/MODSEQ, IDLE, flags, keywords (written exactly as given, purge over `1:*`), Gmail labels, move, append.
- Gmail: OAuth 2 (desktop loopback + PKCE in local mode, server web flow in synced mode) then XOAUTH2 over IMAP/SMTP. Needs a Google Cloud OAuth client ID configured via env/settings.
- Outlook / Microsoft 365: same pattern, later.
- `SmtpMailSender` (nodemailer). `HttpsUnsubscribeSender` posts RFC 8058 one-click unsubscribes to public https URLs only: it resolves the host once, denies every non-global address (including IPv4 embedded in IPv6), pins the connection to the validated IP while keeping the Host header and SNI, and never follows redirects, from the desktop main process in local mode and from the server in synced mode, never from the renderer.
- `MimeParser` (mailparser). `ThreadBuilder` (Message-ID / References / In-Reply-To). `JiraClassifier` (sender + headers + subject patterns, outputs split + task events).

## Tooling

- Internal packages are consumed as TypeScript source (`exports` -> `src`, `moduleResolution: Bundler`, extensionless imports). Vitest, electron-vite and vite-node resolve them, so there is no build step for development or tests.
- Versions are pinned exactly. Native modules (`better-sqlite3`, `argon2`) are allowed to run install scripts via `onlyBuiltDependencies` in `pnpm-workspace.yaml`.
