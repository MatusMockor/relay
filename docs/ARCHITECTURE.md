# Relay - architecture

AI-native mail client in the spirit of Superhuman. Desktop app for macOS and Linux, optional sync server, AI that runs either on the server or locally on the user's machine through the user's own Claude Code / Codex CLI subscription.

## Product modes

| Mode       | Who uses it     | Where data lives                                          | Mail sync                                     | AI                                        |
| ---------- | --------------- | --------------------------------------------------------- | --------------------------------------------- | ----------------------------------------- |
| **Local**  | no registration | SQLite on the device                                      | desktop main process talks IMAP/SMTP directly | local CLI only                            |
| **Synced** | registered user | Postgres on the server, local SQLite cache on each device | server syncs 24/7 (IMAP IDLE)                 | server worker or local CLI (user setting) |

- The user picks the mode on first launch: "Pokračovať bez účtu" (local) or "Pripojiť k serveru" (server URL + register/login).
- The server URL is a per-device setting and can be changed in Settings → Server. Multiple saved servers are allowed.
- In synced mode everything except device-only preferences (window size, panel widths, selected account, server URL, offline window) is stored on the server and pushed to all signed-in devices in real time.
- The server is multi-user from day one: every row is owned by a `userId`. Today it runs on the owner's Linux box, later anyone can self-host it.

## High-level diagram

```
apps/desktop (Electron)
  renderer (React)  ── MailClient interface ──┬── RemoteMailClient ── HTTPS + WebSocket ──► apps/server (NestJS)
                                              └── LocalMailClient  ── IPC ──► main process
  main process: LocalEngine = @relay/engine + @relay/store-sqlite + @relay/mail-core + @relay/ai (local runner)

apps/server (NestJS, Docker Compose on the owner's Linux, optional Cloudflare Tunnel)
  auth/devices · mail accounts · sync scheduler (pg-boss) · REST API · WS gateway · AI worker
  = @relay/engine + Postgres repositories + @relay/mail-core + @relay/ai (server runner) + @relay/mcp-mail (HTTP)
```

## Monorepo layout

```
apps/
  desktop/        Electron app: main, preload, renderer (React)
  server/         NestJS API + workers
packages/
  shared/         domain types, zod schemas, API contract, WS events (no runtime deps besides zod)
  engine/         application services + repository/provider PORTS (interfaces); pure TS, no I/O
  store-sqlite/   SQLite (better-sqlite3 + Drizzle) implementations of engine repository ports
  mail-core/      MailProvider adapters (IMAP via imapflow, Gmail via XOAUTH2), SMTP sender, MIME parsing, threading, Jira classifier
  ai/             AiRunner port + Claude Code / Codex CLI runners, CLI detection, prompts, output parsing
  mcp-mail/       MCP server exposing mail tools backed by engine ports (stdio + streamable HTTP)
  task-systems/   TaskSystemAdapter implementations for external task systems (Jira Cloud today)
  ui/             design tokens and React components (ported from the approved prototype)
  config/         shared tsconfig / eslint / prettier / vitest presets
```

Dependency rule (enforced by ESLint import boundaries):

```
shared  ◄── engine ◄── store-sqlite
   ▲           ▲  ◄── mail-core (implements engine MailProvider/MailSender ports)
   │           ▲  ◄── ai        (implements engine AiRunner port)
   │           ▲  ◄── mcp-mail
   │           ▲  ◄── task-systems (implements engine TaskSystemAdapter)
   ├── ui
   └── apps/* may depend on any package; packages never depend on apps
```

`engine` depends only on `shared`. Everything with I/O lives outside `engine` and is injected.

## Hexagonal core (`@relay/engine`)

- **Ports** (interfaces, one per file) in `engine/src/ports/`:
  - repositories: `AccountRepository`, `MailboxRepository`, `MessageRepository`, `ThreadRepository` (folder-view query with cursor pagination, unified or per account), `LabelRepository`, `SplitRepository`, `AutomationRepository`, `AutomationRunRepository`, `AutomationActivityRepository`, `TaskRepository`, `ReminderRepository`, `DraftRepository`, `ScheduledSendRepository`, `SettingsRepository`, `AiResultRepository`, `AiJobRepository`, `SyncStateRepository` (UIDVALIDITY / last UID / HIGHESTMODSEQ / frozen initial-sync window per mailbox), `MessageBodyRepairRepository` (optional, desktop only: stored messages whose bodies contain U+FFFD and a body-only update), `HistoryBackfillRepository` (optional, desktop only: per-mailbox history cursor, stored UIDs of a candidate list and stored counts per mailbox). User-facing methods take the `UserId` first; sync-internal methods are keyed by account or mailbox.
  - `UnitOfWork.run(work)` passes transaction-bound `Repositories` to `work`.
  - mail: `MailProvider`, `MailProviderFactory`, `MailSender`, `UnsubscribeSender` (RFC 8058 one-click POST), `CredentialVault`, `AttachmentStore`, `MessageParser`, `ThreadResolver`, `JiraClassifier`, `SplitMatcher`, `AutomationMatcher`.
  - AI: `AiRunner` (`run(request): AsyncIterable<AiEvent>`), `AiRunnerRegistry`.
  - task systems: `TaskSystemAdapter`, `TaskSystemAdapterRegistry`, `TaskSystemConnectionRepository` (in `Repositories`), `TaskSystemSecretStore`.
  - infrastructure: `EventPublisher`, `Clock`, `IdGenerator`, `Logger`.
- Engine-internal types (raw/parsed messages, sync cursors, pages, AI requests) live in `engine/src/model/`. They never cross the wire.
- `PORT_TOKENS` (`engine/src/tokens.ts`) gives every port a `Symbol.for('relay.engine.<Port>')` token, used by Nest providers and the desktop composition root.
- `EngineError` subclasses (`NotFoundError`, `ValidationError`, `ConflictError`, `ForbiddenError`, `ProviderError`, `NotImplementedError`) carry an `ApiErrorCode`; HTTP and IPC adapters map them to the shared error shape.
- **Application services** in `engine/src/services/`, one use case family per file: `SyncService`, `InboxQueryService`, `ThreadQueryService`, `MessageBodyService` (on-demand bodies of header-only messages), `ServerSearchService` (full-text search on the mail server for mail whose body is not stored), `MessageActionsService` (done, undo, trash, restore, report spam / not spam, move to a folder and undo the move, read/unread, label, pin), `LabelService` (create, rename, recolour and delete labels), `ReminderService`, `ComposeService`, `TaskService`, `SplitService`, `AutomationService`, `AutomationHistoryService`, `AiService`, `FolderService` (creates, renames, moves and deletes custom folders and Gmail labels on the mail server), `TaskSystemService` (connections to external task systems and their live ticket lists), `UnsubscribeService` (parses the stored `List-Unsubscribe` / `List-Unsubscribe-Post` headers into https or mailto options and sends one-click unsubscribes).
- All database access goes through repository ports. No service, controller or IPC handler talks to Drizzle directly.
- Server implements the ports with Postgres + Drizzle; local mode implements them with SQLite + Drizzle (`store-sqlite`). The same services run in both places.

## Domain model (see `packages/shared/src/domain`)

`User`, `Device`, `MailAccount` (provider: `imap` | `gmail` | `outlook`, color, isPrimary, sync interval, status), `ImapSmtpSettings`, `AccountCredentials` (password or OAuth tokens, never sent to clients), `Mailbox` (role: inbox, sent, drafts, trash, archive, spam, custom, label, system; `subscribed`, `uidValidity`), `Message`, `ThreadSummary` / `ThreadDetail`, `ThreadAction`, `Label` (`kind`: `keyword` for IMAP keywords or `gmail` for Gmail labels, `remoteName` is the keyword or the Gmail label path), `Split` (rule-based view of the inbox), `Automation` (rule that runs actions on new mail), `Task` (one per Jira issue or created by AI), `Reminder`, `Draft`, `ScheduledSend`, `AiJob` / `AiResult` / `AiEvent`, `UserSettings` (synced), `DeviceSettings` (device-only), `FolderView`, `TaskSystemConnection` and `ExternalTask` (see Task systems).

- Ids are branded strings (`UserId`, `ThreadId`, ...) and timestamps are ISO 8601 strings with offset, so the same types work over HTTP, WebSocket and IPC.
- `Task.priority` (`TaskPriority`: `urgent`, `high`, `medium`, `low`, `none`; `shared/src/domain/task-priority.ts` with `TASK_PRIORITIES` and `taskPriorityRank`) is `none` by default (SQLite `0035`, Postgres `0034`, both `NOT NULL DEFAULT 'none'`, and the schema defaults a missing field to `none` for older peers). `PATCH /tasks/:id` and IPC `local.tasks.update` accept `priority`. Task lists order by priority rank (urgent first, none last), then by `updatedAt` and id descending; the cursor carries the rank. The AI `createTask` answer may suggest a priority from the urgency in the mail (missing or invalid becomes `none`), the MCP `create_task` tool accepts one and `list_tasks` shows it; Jira and automation tasks start with `none` and a reopened Jira task keeps its priority. The `tasks` folder view is ordered in the stores (SQLite, Postgres, the engine memory adapter and the demo client alike): each thread's active task is its open or waiting task with the best priority (then the latest change, then id), and threads sort by that rank (no active task last), then by the last message and id, with all three in the folder cursor. Only this view returns `ThreadSummary.activeTask` (`{ id, priority }`, optional and nullable, `thread-active-task.ts`); `writeThreadToLists` keeps a listed `activeTask` when a thread event carries none. On desktop the view ("Moje úlohy") groups its rows under priority headers from that projection (`features/tasks`), and keyboard navigation follows that order. `P` then `1` to `4` or `0` (by `KeyboardEvent.code`, so it works on Slovak layouts) or the palette commands "Priorita: ..." change the priority. Any other key after `P` cancels the chord and runs normally, and a folder, selection, open thread or overlay change cancels it too. Writes are last intent wins: they run one at a time per task in the order chosen (a queued write that a newer choice replaced is skipped), a pending store shows the latest choice until it settles, earlier writes neither roll back nor show errors, the caches are refreshed when the queue of the task drains, undo is offered only after a successful write and goes back to the last confirmed priority before it, and a server that answers with another priority or lists the view without `activeTask` (an older server) gets "Server je starší a nepodporuje priority úloh. Aktualizuj server."
- A `Split` matches a message with the same condition language as automations: `match` (`any`, the default that keeps the earlier OR semantics, or `all`) over its `rules`, minus optional `exceptions` (at most 20), evaluated by the shared `matchesCriteria` (`splitCriteria` in `shared/src/domain/split-criteria.ts` maps a split onto automation criteria, `RuleSplitMatcher` uses the same `evaluateRule` as `RuleAutomationMatcher`). Split rules accept `fromDomain`, `fromAddress`, `subjectRegex`, `header`, `jira`, `subjectContains`, `recipient` (To / Cc) and `hasAttachment`; `jiraEvent` is not offered because membership is re-evaluated from stored messages where the Jira event kind is not known (the evaluator only knows the thread's Jira key). The ingestor passes To, Cc and the file attachment flag to the split matcher like the stored match subjects do, so new and re-evaluated mail match alike. Splits stored before the fields existed read as `any` with no exceptions (SQLite `0034`, Postgres `0033`). In `SplitInput` both fields are optional: a replace that omits them (an older client) keeps the stored values of an existing split and uses the defaults for a new one. Responses are `SplitEntry` lists like automations: a split whose `match`, `rules` or `exceptions` this version cannot parse becomes `{kind: 'unsupported', id, name, order, accountId, exclusive, hideTasks}` (tabs keep working, Settings shows it read-only) and a replace sends it back as `{id, keep: true}`, which keeps the stored split at its new position. The SQLite and Postgres read paths parse per split as well: repositories return such rows only from `SplitRepository.listUnsupported`, so the matcher, the preview and the overlaps never see them, while re-evaluation keeps the threads already in an unsupported split there (new mail does not join it) and its tab still lists them. A replace never deletes an unsupported split, even when a stale client omits its keep marker: the engine appends omitted unsupported splits after the listed ones (they count toward the limit of 50) and the stores delete only rows they can read, so only a version that understands the split can remove it. Before a replace that uses `all`, exceptions or the newer condition types, `RemoteMailClient` reads the raw split list and refuses to write with "Server je starší a nepodporuje režim podmienok ani výnimky v splitoch. Aktualizuj server." when the server returns splits without `match`; with an empty list it writes, compares the returned splits with the request and, when an older server dropped `all` or exceptions, empties the list again and fails with the same message; a 404 from the preview becomes "Server je starší a nepodporuje náhľad splitu. Aktualizuj server." `accountId: null` means the split applies to the unified inbox. An `exclusive` split removes matching threads from the main inbox. A `hideTasks` split leaves out threads that are in Úlohy (have a task that is not done).
- Split preview (`SplitService.preview`, `POST /splits/preview`, IPC `local.splits.preview`): the split editor sends the unsaved draft (`splitId`, account, match, rules, exceptions) and gets the automation preview answer (`RecentMatches`, the same 30 day candidates and matcher as the automation preview) plus `overlaps`: for every earlier split (lower `order`; every saved split for a new one) and every enabled automation with an `archive` or `moveTo` action whose scope covers the account, how many of the previewed threads it also catches (`SplitOverlapFinder`; the split itself and split rivals evaluate `jira` from the thread's Jira key like membership does, automation rivals use the per-message classification, loaded once per account for all of them), shown as "2 maily zachytí aj split Jira, ktorý je vyššie". The demo client computes the same from its state (`demo-splits.ts`) and re-evaluates the membership of splits whose rules or scope changed when splits are replaced. "Vytvoriť pravidlo z mailu" has a secondary "Zaradiť do splitu…": a checked single condition joins an existing `any` split of the mail's account (or of all accounts); several conditions or an `all` split need a new split, which is created on the mail's account with `match: all` for several conditions and then opened in the split editor. The dialog files only once the split list has loaded and re-reads it right before the replace. A split edit that the server refuses stays in the editor as unsaved with the error, so it can be corrected and saved again. A sync that ingested mail with splits that changed meanwhile re-evaluates the account's split membership when it ends (`SplitSnapshotGuard`), so an edit racing a sync never leaves new mail filed by the old rules.
- An `Automation` runs when its conditions match a new inbox message (split rule conditions, the Jira event kind, a recipient address or domain in To / Cc, "has a file attachment" and `subjectContains`, a substring of the subject compared ignoring case and diacritics). `match` (`all`, the default, or `any`) says whether every condition or at least one must match, and a message that matches any of the optional `exceptions` (same condition types, at most 20) is skipped; `matchesCriteria` in `shared/src/domain/automation-criteria.ts` holds that rule for the live runner, apply-to-existing and the demo client. Rules stored before the fields existed read as `all` with no exceptions (SQLite `0032`, Postgres `0031` add the columns with those defaults). Both fields are optional in `AutomationInput`: a replace that omits them (an older client) keeps the stored values of an existing rule and uses the defaults only for a new one. `RemoteMailClient` compares the rules a replace returns with the request and fails with "Server je starší a nepodporuje režim podmienok ani výnimky. Aktualizuj server." when a server that predates the fields dropped `any` or exceptions; a 404 from the preview endpoint becomes "Server je starší a nepodporuje náhľad pravidla. Aktualizuj server." The editor shows a live preview of the unsaved draft (`AutomationService.preview`, `POST /automations/preview`, IPC `local.automations.preview`, debounced 400 ms): `AutomationCandidateRepository.listRecent` reads up to 500 threads of each of the rule's accounts outside trash and spam that have a message received in the last 30 days outside sent, drafts, trash and spam mailboxes, with only those messages, `AutomationBacklogMatcher` matches them like apply-to-existing does, and the answer is `{days, count, truncated, samples}` with the 5 newest matching threads (sender, subject, date); `truncated` means an account hit the 500 thread limit and the editor then says "Zachytí aspoň N mailov". Candidate lists (`listInbox` and `listRecent`) carry at most the 50 newest messages per thread (`CANDIDATE_MESSAGES_PER_THREAD`, a `row_number()` window in both stores). Jira classification is loaded only when the conditions or exceptions use `jira` / `jiraEvent`, only for the candidate messages of Jira threads, in batches of 500 through `AutomationCandidateRepository.findMessages`. Nothing is saved or claimed. In the editor, the subject regular expression and header conditions are offered only from the collapsible Pokročilé section (for Keď or Okrem, and not while that section has an unsaved row); rows that already use them stay editable. Adding stops at 20 conditions and 20 exceptions. The preview also sees condition rows that are being typed and are already valid (an invalid row keeps its saved value), while saving still happens on Enter or blur. "Vytvoriť pravidlo z mailu…" (thread row context menu and command palette, overlay `ruleFromMail`) opens a compact dialog built from the newest message of the thread that is not from one of the user's accounts: "Je to newsletter <odosielateľ>" (only when `getUnsubscribeOptions` reports an https or mailto `List-Unsubscribe` target, since `List-Id` never reaches clients; it adds a `header` condition `List-Unsubscribe` `.+` and `fromAddress`), "Od <adresa>", "Z domény <doména>" and "Predmet obsahuje" (the subject without reply and forward prefixes, at most 60 characters). Checked options are combined with `match: all`, the default is the newsletter option when offered, otherwise the sender, and the rule is scoped to the thread's account and named after the strongest chosen option. "Vytvoriť" saves through the same replace path as the editor and can run apply-to-existing right after; "Upraviť podrobne" opens the editor with the rule as an unsaved draft, which "Uložiť pravidlo" (or any change) saves. The demo client evaluates `jira` from the thread's Jira key and answers `header` conditions only for `List-Unsubscribe`, from its own unsubscribe table; it has no Jira event kinds, so `jiraEvent` conditions never match there, and a rule with a `jiraEvent` or `header` exception is refused. The Jira preset matches the stored message (`matchSubjectOf`, so attachment and recipient conditions work) and falls back to the event's title, sender and headers when the message is gone. Actions are objects discriminated by `type`: AI summary, AI-judged task, AI reply draft (`draftReply`), notification, mark read, pin (IMAP `\Flagged`), archive, `addLabel {labelId}`, `moveTo {mailboxId}`, `remind {afterDays}` (1 to 30 days) and `forward {to}` (an address checked by the shared email schema). A rule holds each simple action and each label at most once, at most one `moveTo`, `remind` and `forward`, and at most one of the placement actions `remind`, `moveTo` and `archive` (`PLACEMENT_ACTION_TYPES`; the editor swaps them with a "Nahradí …" note); inputs still accept the legacy string actions (`'task'`), and data migrations (SQLite `0024`, Postgres `0026`) rewrote stored string arrays to objects. The runner executes actions in the fixed order notify, summary, task, draftReply, forward, markRead, pin, addLabel, remind, moveTo, archive, so flags and labels are written before the move changes locations; `remind` snoozes the thread through `MessageActionsService` `remind` (the same reminder the user sets with "Pripomenúť…", the mail stays in the server inbox) and records the exact reminder it created (`reminder: {id, remindAt}` on the activity action); `forward` goes through the compose pipeline exactly like a manual forward (`ComposeMailForwarder`: a draft from the account of the mail with "Fwd:" and the quoted body, the non-inline attachments copied by `forwardAttachments`, sent by `DraftSender`, which records the Sent copy and removes the draft; a failed send removes the draft too) and refuses mail sent from one of the user's own accounts. Automatic forwards carry `Auto-Submitted: auto-forwarded` and `X-Relay-Automation: forward` (RFC 3834, `OutgoingMessage.headers`), and a message is never forwarded automatically when it carries the Relay marker, `Auto-Submitted` other than `no`, `Precedence: junk` or `auto_reply`, `X-Autoreply` or `X-Autorespond` (bulk and list mail such as newsletters can still be forwarded). `ForwardRateLimit` allows at most 20 automatic forwards per account per hour, counted from the `ok` forward outcomes in the activity log (`AutomationActivityRepository.countOkActionsSince`). A refused action (`AutomationActionRefusal`) is logged and recorded as `failed` with a Slovak `reason` that the history chip shows; `draftReply` queues an `automationDraft` AI job on the rule's runner, model and instructions, and the result applier saves the reply as a draft in the thread (to the Reply-To or sender of the triggering message, "Re:" subject) unless the thread already has a draft, so the user reviews, edits or deletes it and nothing is sent; `moveTo` goes through `MessageActionsService` `move` for the whole thread (a real IMAP MOVE, or label plus archive for a Gmail `label` mailbox) and `addLabel` through `addLabel`. A failing action, such as a target folder or label deleted after the rule was saved, is logged and the remaining actions still run; the client marks such tokens as "Priečinok už neexistuje" / "Štítok už neexistuje" by comparing the targets with the account's mailboxes and labels. `forward` needs an account scoped rule as well and never targets the address of the rule's account (`AutomationForwardValidator`); `moveTo` and `addLabel` need an account scoped rule: `AutomationService` rejects them on a rule for all accounts and validates that a newly added target belongs to the rule's account and that a move target has role `custom`, `label`, `inbox` or `archive` (targets already stored on that rule are not re-validated, so a rule whose folder disappeared can still be edited). Automation moves leave the usual `move-origin` records; they are per thread and expire after the 1 hour undo window, so they only let the user undo that thread's move and never affect other threads. "Použiť aj na existujúce" (`AutomationService.applyToExisting`, `POST /automations/:id/apply`, IPC `local.automations.apply`) reads the newest 500 inbox threads of each of the rule's accounts with their messages' match subjects through `AutomationCandidateRepository` (served by the existing account/state/last-message indexes), matches each message against the rule and keeps the newest 500 matching threads. Jira conditions use the real per-message classification, recomputed from the stored message with the same `JiraClassifier` the ingestor uses, never an invented event kind. Only the mail actions (`MAIL_AUTOMATION_ACTION_TYPES`: mark read, pin, label, remind, move, archive) run; `forward` and `draftReply` are live only (`LIVE_ONLY_AUTOMATION_ACTION_TYPES`) and their handlers also refuse a non-live arrival. Applies are serialized per rule in process; each thread is re-read and skipped unless it is still in the inbox, and it is gated by claiming its newest matching message in `AutomationRunRepository` (the other matching messages are claimed too), so concurrent or repeated applies never run a thread twice. When an action fails, the thread counts as `failed` and its claims are released so a later apply retries it; mail actions are idempotent, so the actions that already succeeded are harmless to repeat. The result is `{matched, applied, failed}`. Each rule picks its AI runner, a model and effort from the static catalog in `shared/src/domain/ai-model-catalog.ts`, and optional instructions. Rules never run on the initial sync backlog, and `AutomationRunRepository` records each automation and message pair so a rule fires at most once per message. The seeded `Jira tasky` preset starts turned off; once the user turns it on it keeps the classic Jira task behavior (create or reopen by Jira key without AI) until the user adds instructions or turns it off again. Presets already stored keep their `enabled` value, and without a stored preset no Jira task is created. Like any other rule it can be renamed, scoped to one account, edited or removed. Removing it records the preset in `removed_automation_presets` (SQLite `0026`, Postgres `0028`) through `AutomationRepository.markPresetRemoved`, so `AutomationService` never seeds it again; "Obnoviť predvolené Jira pravidlo" (`AutomationService.restoreDefault`, `POST /automations/restore-default`, IPC `local.automations.restoreDefault`) clears that record and seeds it again, turned off. Which Jira event kinds create or reopen such a task is the user setting `jira.taskEvents` (default `mention` and `assigned`); other kinds create nothing and leave an existing task untouched.
- Rules from a newer Relay version: automation lists (HTTP responses, IPC results, the `automations.updated` event and the SQLite and Postgres read paths) are parsed per rule with `AutomationEntriesSchema`. A rule that fails only because of its actions, conditions or exceptions (an unknown type or a widened range) becomes an `UnsupportedAutomation` (`kind: 'unsupported'`, id, name, enabled, order, account) that the list shows read-only as "Pravidlo z novšej verzie Relay, aktualizuj aplikáciu"; anything else broken still fails. Repositories return such rows only from `listUnsupported`, so the runner, apply-to-existing and preview never see them. A replace never deletes an unsupported rule, even when a stale client omits it (it is appended after the listed rules and counts toward the limit of 50; the stores delete only rules they can read). A replace may name a rule as `{id, keep: true}` to keep it exactly as stored except for its position, which becomes the marker's index in the replace list, and the renderer puts this marker for every unsupported rule at that rule's index in the cached list and numbers all rules by their index, so editing other rules never deletes or moves it. Restoring the default Jira rule counts unsupported rules toward the limit of 50.
- Rule history (História pravidla): after the live runner or apply-to-existing executes a rule's actions on a message, `AutomationActivityRecorder` appends one `AutomationActivity` (`automation_activity`, SQLite `0033`, Postgres `0032`, indexed by user, rule and creation time) with the thread, message, sender and subject, `source` (`live` or `apply`), `undoneAt` and every executed action with its outcome (`ok` or `failed`), `changed` (the ids of the messages the action really changed: for mark read, pin and label the exact messages the write targeted, returned by `MessageActionsService.applyTracked` from the same snapshot the write used; for archive and move the messages the state-move plan moved or labelled plus their other copies of the same physical message, so a Gmail copy merged into All Mail still counts; a write that committed before a later step failed, or whose thread event could not be published, is still recorded as `ok` with its targets), `origins` (the move-origin records the move wrote, by message and revision), `labelled` (the messages a Gmail move newly labelled; undo removes the label only from these), `previousState` (the thread state before the action) and `undo` (the persisted result of its reversal). A recording failure is logged and never fails the run. Each append prunes the rule's entries older than 90 days and keeps at most the newest 1000 (a soft cap: concurrent appends can briefly exceed it until the next append); removing the rule or the account removes its history. `AutomationHistoryService` (`GET /automations/:id/history`, IPC `local.automations.history`) returns the 50 newest entries and stats for the last 30 days (runs, failed actions, last run). Undo (`POST /automations/:id/history/:entryId/undo`, IPC `local.automations.undoActivity`) re-reads the thread, skips it while it is in trash or spam, and reverses only the successful mail actions that changed something, in the order archive, moveTo, remind, addLabel, pin, markRead, through `MessageActionsService`: remind cancels the reminder (`cancelReminder`) only while the exact reminder the run recorded (id and `remindAt`) is still active and unchanged, so a reminder the user rescheduled, one another rule replaced or one that fired is left alone (an entry with a recorded reminder counts as changed even though no message was written); markRead, pin and addLabel are reverted only on the recorded messages that still carry the change (`MessageActionsService.revert`), so read state, flags and labels the user already had stay; archive returns only the recorded messages that are still in the archive to the inbox, and only when the thread came from the inbox and is still filed away and not marked Done; moveTo only while the thread is still in the target folder (or carries the Gmail label), first through the `move-origin` records (`undoMove`) only while every record of the thread is one this move wrote (same message and revision), and, when those expired or a later move replaced them and the thread came from the inbox, by returning the recorded copies still in the rule's destination to the inbox and removing the Gmail label only from the recorded messages (a thread already back in the inbox only loses the label; a move to the inbox, or of a thread that did not come from the inbox, is reversed through `undoMove` alone). Notify, AI summary, task, forward and AI reply draft are reported `notUndoable` (tasks are never deleted, a sent forward cannot be recalled and an AI draft stays for the user to edit or delete; history chips of these actions are marked "Nedá sa vrátiť"), failed or no-op actions and actions of a missing or changed thread are `skipped`. Each action's reversal result is stored, so a retry after a partial failure only repeats the failed reversals; an entry is marked undone when no reversal failed and it had a reversible action, so undo is idempotent (`alreadyUndone`). "Vrátiť všetko z dneška" (`POST /automations/:id/history/undo-since`, IPC `local.automations.undoSince`) undoes every open undoable entry of the rule created since the client's local midnight, computed when the button is pressed. Undo calls are serialized per user and scoped to the rule's owner. The demo client keeps the same log in memory, records its apply-to-existing runs with the same effects and seeds a few entries for the seeded rules.

Marking a conversation Done in Relay records an explicit completion and archives its inbox messages (IMAP move to archive mailbox / Gmail remove INBOX label). The Done view lists only explicitly completed conversations. The Archive view contains the other conversations filed out of the inbox, including older data whose completion history is unknown. Read state, mailbox moves and labels are mirrored to the mail provider.

- Sync covers the mailbox roles inbox, sent, archive, trash, spam and custom (`DEFAULT_SYNC_OPTIONS.mailboxRoles`). A missing archive, sent, trash, drafts or spam (`Junk`) mailbox is created on first use (`RoleMailboxEnsurer`).
- The initial sync is inbox first: it reads the inbox window, downloads and flushes its newest `firstBatchSize` (15) messages together with their parents from the other synced mailboxes (found by Message-ID in the mailboxes still in their initial sync, only within the initial window, so a reply never lands in a thread of its own), and only then reads the windows of the other mailboxes. The rest goes in `batchSize` (50) chunks, newest conversation first, with conversations that touch the inbox ahead of the others. Replies without reply headers stay out of the first batch, and when a parent search fails the first batch is skipped, so both keep the parents-first order. Gmail copies (INBOX, All Mail, Sent) stay separate messages per mailbox, so each copy is still downloaded. A mailbox window lists only the UIDs it needs: the newest `initialMessageLimit` messages by sequence number (`listUids(path, { newest })`: NOOP, then `UID SEARCH <exists-n+1>:<exists>`), or on resume the UIDs from the frozen `floorUid` up. The mailbox refresh reads STATUS only of newly listed mailboxes while a known one disappeared (rename detection by UIDVALIDITY); selected mailboxes get their status when they are opened, and every other mailbox without a stored UIDVALIDITY (Gmail labels, system and unsynced folders) is probed once after the selected mailboxes are synced (`deferred-status-probe.ts`), so hundreds of Gmail labels no longer delay the first message. The initial sync reports account-level `sync.progress` events (`mailboxId` null, phase `messages`) with an optional `stage`: `headers` (mailboxes whose window was read / mailboxes in their initial sync), `inbox` (the first batch, 0 / n before and n / n after it) and `backlog` (processed / total over every window, after each chunk); per-mailbox `messages` events stay as before. `stage` is optional and an unknown value parses as absent (`.catch(undefined)`), so older clients and servers keep parsing the event. The renderer keeps the latest account-level event per account in the query cache (`['mail','sync','progress',accountId]`, `use-sync-progress.ts`, fed by `sync.progress` from IPC `local.events` and the WebSocket) and Settings → Účty shows it on the account's Stav row while the account is `syncing`: "Načítavam zoznamy správ… 2 / 6 priečinkov", "Sťahujem najnovšiu doručenú poštu… 0 / 15" or "Sťahujem nedávnu poštu… 120 / 1 800" with a progress bar; an event without a stage shows only the status. An `account.status` other than `syncing` clears the account's entry (a failed sync emits no `idle`) and refetches the history progress when the cached entry of that account is `waiting`.
- Custom folders (`custom`, plain IMAP) are synced when subscribed, or all of them when the server reports no subscriptions at all. The first pass takes the newest `initialFolderMessageLimit` (200) messages regardless of age. Mail that lives only in a custom folder is `done`; custom folders create no Jira tasks, calendar invitations or inbox arrivals. A mailbox whose UIDNEXT, message count and HIGHESTMODSEQ did not change since the last complete pass is skipped.
- Gmail (detected by the `X-GM-EXT-1` capability) is modelled as labels, not folders: every non-special mailbox gets the role `label` and is never synced. Each `label` mailbox has one `Label` with `kind: 'gmail'`, kept in step by `GmailLabelCatalog` during the mailbox refresh, and message membership comes from `X-GM-LABELS` on the copies Relay already syncs (INBOX, All Mail, Sent, Spam, Trash). When labels are added, the synced copies are rescanned for labels. `\Flagged`, `\Important` and other virtual folders get the role `system` and are neither synced nor shown. Plain IMAP labels are keywords (`kind: 'keyword'`); `Junk`, `NonJunk`, `NotJunk` and `$`-prefixed keywords are ignored.
- The mailbox refresher detects remote renames: a vanished mailbox and a new one with the same UIDVALIDITY and message count (one candidate only) are treated as one mailbox, so its id, messages, sync state and Gmail label survive. Anything ambiguous is forgotten and downloaded again. Refreshes that change the mailbox list or labels emit `mailboxes.updated` and `labels.updated`.
- `ThreadState` is `inbox`, `done`, `trash`, `spam` or `reminder`. Trash and spam are holding states: a thread whose mail (ignoring Sent copies) sits only in that mailbox gets that state (spam when it is split between Spam and Trash), and it leaves it once its mail is elsewhere. Generic actions like done refuse a held thread; restore or not spam brings it back.
- Folder views (`FolderView`): `inbox`, `tasks`, `reminders`, `done`, `sent`, `drafts`, `scheduled`, `spam`, `trash`, `mailbox` (threads with a message in `mailboxId`) and `label` (threads carrying `labelId`, in any state except trash and spam). `spam` and `trash` show threads in that state; every other view leaves them out.
- Thread list search and filters (`ThreadListQuery` -> `ThreadFolderQuery`): `q` matches word prefixes of subject, sender, snippet and text body; every term must match. `searchField` (`from` or `subject`) limits the terms to the sender or the subject (SQLite FTS5 column filters on `sender` / `subject`; Postgres tsquery weight `A` for the subject, and for the sender the indexed weight `B` match narrowed by a sender-only tsvector over the from name and email, so recipients never match `from`). `unread` keeps unread threads, `hasAttachment` keeps threads with a non-inline attachment on a message that matched the search (any message without `q`). `everywhere` replaces the view, split, label and mailbox scope with every state except trash and spam; the account scope stays. The booleans arrive as `true` / `false` query string values. `searchField` without `q` has no effect.
- "Report spam" moves the received (inbox, archive and custom folder) mail of a thread to the spam mailbox and remembers where each message came from, including the exact custom folder; "Not spam" moves it back there (inbox when unknown or when the folder no longer exists). Trash remembers origins the same way, so a trashed spam thread is restored to spam and trashed folder mail returns to its folder.
- "Move to" (`{ type: 'move', mailboxId }`) takes the inbox, the archive, a custom folder (plain IMAP) or a Gmail `label` mailbox. On plain IMAP the received copies (inbox, archive, custom, spam and trash, never Sent) that are not already there are moved with IMAP MOVE; the thread becomes `inbox` when the target is the inbox and `done` otherwise, so a held thread leaves trash or spam and its trash and spam origins are forgotten. On Gmail it is Gmail's own "Move to": the label is added to every local copy and written once per physical message through `X-GM-LABELS` (`MailProvider.setLabels`, preferring the All Mail copy), then the inbox, spam and trash copies move to All Mail and the thread becomes `done`. Moving to where the thread already is changes nothing. Gmail move sources and label ownership are decided per physical message (email id, Message-ID when it is missing), so a label any copy already had is never removed by undo. Each move records a `move-origin` per moved or newly labelled message (its previous mailbox, the Gmail label it added and the trash and spam origins it displaced); `{ type: 'undoMove' }` returns those messages to their previous mailboxes (inbox when that folder is gone), puts the displaced trash or spam origins back and removes the added label. Writing a Gmail label op drops a queued op for the same label on another copy of the same message. A new move of the thread replaces its records, and records older than the one-hour undo window are dropped before every move and undo.
- When a move's COPYUID points at a row Relay already stores in the target (Gmail returns the existing All Mail UID on archive), or on Gmail without a returned UID a row with the same email id is already there, the replayer deletes the moving row instead of moving it, carries its trash, spam and move origins and reply drafts over to the surviving row and journals a thread refresh. A later draft save that still names the deleted row keeps the stored reply reference.
- Labels (Štítky) are managed by `LabelService` (`POST /labels`, `PATCH /labels/:id`, `DELETE /labels/:id`, IPC `local.labels.*`). Names are trimmed, 1-100 characters and unique per account ignoring case (both stores keep a `name_key` column, NFC plus Slovak lower case, with a unique index, and a clash becomes `ConflictError` "Štítok s týmto názvom už existuje."; the key is recomputed only when the name changes, and after the migrations each store rewrites keys that differ from that normalization, giving older labels that collide ignoring case a `\u0001` + id suffix); Gmail names may not start with `[Gmail]` or contain `\`. Colours are Relay-only. Every change emits `labels.updated` (Gmail changes also `mailboxes.updated`).
  - Keyword labels (plain IMAP): creating one stores only the local row (IMAP has no keyword list). `remoteName` is the exact keyword on the server and never changes, so a rename only changes the display name, and adds, removes and purges always write the stored `remoteName`. A new label gets its keyword from `services/labels/keyword-codec.ts`: a name that is a plain IMAP atom without `&` stays as it is, anything else (including every `&`) is encoded as `&` + lowercase hex of the UTF-8 bytes + `-` per run ("Faktúry" becomes `Fakt&c3ba-ry`), which survives servers that fold case. Adopted server keywords are decoded only for the display name, and foreign keywords that are not such encodings are shown as they are. Keywords are compared ignoring case. Names the server reserves (`$...`, `Junk`, `NonJunk`, `NotJunk`) cannot be created. A new keyword may be at most 50 characters after encoding (Dovecot's default `mail_max_keyword_length`), otherwise creation fails with "Názov štítka je pre server príliš dlhý."; renaming changes only the display name and is not limited by it. A server whose `PERMANENTFLAGS` lack `\*` rejects new keywords with `ProviderError` "Server nepodporuje vlastné štítky". Deleting a label removes the row, refreshes its threads and queues a `keyword-purge` that runs `UID STORE 1:* -FLAGS` on every synced mailbox (right away, otherwise on the next sync). The purge record stays as a tombstone until a sync that started after the purge has completed, and while it exists sync never recreates a label from that keyword. A server keyword whose name is already taken by a renamed label is adopted with a numbered name.
  - Gmail labels: create, rename and delete go to Gmail first (`MailProvider.createMailbox`, `renameMailbox`, `deleteMailbox`) and then update the `label` mailbox row and the Label; a rename moves nested labels (`Projekty/...`) with it, keeps their ids and retargets queued `X-GM-LABELS` writes for the renamed tree in the same transaction, a delete keeps the mail in All Mail and clears the label from local threads. Adding or removing a Gmail label on a thread changes every local copy and writes `X-GM-LABELS` once per physical message, preferring the All Mail copy.
- Folder management (`FolderService`, `POST /accounts/:id/mailboxes`, `PATCH /mailboxes/:id`, `DELETE /mailboxes/:id`, IPC `local.mailboxes.*`) changes only `custom` mailboxes (plain IMAP) and `label` mailboxes (Gmail). INBOX, every role mailbox, `system` mailboxes and the `[Gmail]` tree are refused with `ForbiddenError`. Names are trimmed and must not contain the hierarchy delimiter, `*` or `%`, must not be INBOX and must not clash with a sibling (ignoring case). The operations run online against the mail server and are never queued; without a connection they fail with `ProviderError`. Rename and move are one IMAP RENAME (the new path and its subscribed subfolders are subscribed, the old paths unsubscribed), then `relocateTree` moves the stored mailbox and every descendant path, so mailbox ids, messages, sync state, automation `moveTo` targets and the sidebar selection survive; for Gmail the same transaction runs the label service's `relocateLabelTree`, so the matching `gmail` Labels keep their ids and queued `X-GM-LABELS` writes are retargeted. Renaming, moving or deleting a folder is also refused when a stored or listed mailbox inside it is protected. Deleting a plain IMAP folder is refused while it has subfolders (stored or listed). Otherwise, within one connection, every message the server lists in the folder (not only the cached ones) is moved to Trash, for at most three rounds; cached copies keep their rows and get trash origins (restore goes to the inbox once the folder is gone), but only when the stored UIDVALIDITY of the folder (and of Trash, once Trash has been synced) still matches the server, otherwise the move is server-side only and the next sync rebuilds Trash. DELETE is sent only right after STATUS reports 0 messages and a fresh UID search (`listUids(path, { fresh: true })`: NOOP plus an unconditional `UID SEARCH ALL`) of the selected folder is empty. Threads whose mail was already moved are refreshed even when a later step fails. A failed, partial or ambiguous move, or mail that keeps arriving, aborts and keeps the folder; mail already moved stays in Trash. The only remaining gap is mail delivered in the single round trip between that last check and DELETE, which IMAP gives no way to close. After the DELETE the folder is forgotten. Deleting a Gmail label deletes only the label: the mail stays in All Mail, and the label service's `LabelRemoval` drops queued writes for it, removes the Label and its mailbox row and refreshes the affected threads. Each change emits `mailboxes.updated`, and `labels.updated` for Gmail.
- A `Message` carries an optional `bodyState` (`local` | `remote`, absent means local; `isBodyLocal` in `shared`). Remote rows are header-only history rows: subject, addresses, snippet, flags, labels and attachment metadata are stored, text and HTML bodies are `null`. SQLite stores it as `messages.body_state` (`NOT NULL DEFAULT 'local'`, migration `0029`, which also adds `messages_account_body_date_idx (account_id, body_state, date_ts)` for the later offline window); Postgres has no column and always reads local.
- History backfill (`services/sync/history`, driven on desktop by `HistoryBackfillScheduler`, never on the server): `SyncService.backfillHistory(userId, accountId)` runs one bounded slice and returns `HistorySliceReport` (`{ skipped: true, reason: 'busy' | 'unsupported' }` or `{ skipped: false, processed, more, perMailbox }`). It needs the optional `historyBackfills` dependency (SQLite only, wired in `local-engine.ts`); without it the report is `unsupported`. Per-account exclusivity lives in `AccountRunQueue`: a sync and a history slice never run together, a sync requested during a slice is queued and the slice yields after its current batch (`shouldYield`, also when a server search ingest is waiting, see Server search), and a slice is skipped while a sync runs or is queued. A slice (`sync.history`, defaults 500 messages, 15 s, batches of 100) walks the mailboxes with a completed initial sync in the order inbox, sent, archive (Gmail All Mail), custom, spam, trash (Gmail `label` mailboxes stay excluded). Each mailbox has a cursor (`history_backfill`: uid validity, `below_uid`, `done_at`) that starts at `last_uid + 1` of the sync state, so the gap below the initial window is filled too, and restarts when the UIDVALIDITY of the sync state changes; a mailbox whose server UIDVALIDITY differs from its sync state is skipped until the next sync resets it. `history-window.ts` searches UID ranges newest first (`listUids` with `range`, 2000 UIDs growing x4 while empty, capped), drops UIDs already stored, and the batch is read with `fetchSummaries` (no message sources) and ingested by `MessageIngestor.ingestSummary`: the header block is parsed by the normal `MessageParser`, the snippet and attachment list come from the summary, bodies are `null`, trace headers (`TRACE_HEADERS`, shared with mail-core) are dropped and the row is stored `remote`. History rows are quiet: they journal only a thread refresh (with the mailbox role and split matches), never message effects, Jira events or calendar parts, so no automations, AI one-liners, notifications, tasks or invitations come from old mail. The history slice journals with a quiet `SyncJournal`, so its `thread-refresh` work carries `quiet: true` (merging it with work from a regular sync clears the flag, and rows without the flag are regular). `ChangeFlusher.flushThreads` (also the first step of `flush`) refreshes the pending threads, emits `thread.upserted` / `thread.removed` for regular work and, whenever any quiet work was refreshed, exactly one `threads.changed {accountId, count}` with the number of quiet threads, never a per-thread event for them; the renderer then refetches thread lists and that account's cached thread details. So history threads stay silent even when a regular sync flushes their leftover work after a failed batch, while regular syncs keep per-thread events because new-mail notifications and the tray overview rely on them. A mailbox slice flushes leftover thread work before it moves the cursor, and every batch is flushed before the cursor passes it, so a failed ingest or flush never leaves a range behind the cursor with stale thread summaries. The cursor is saved after every batch, after the thread refresh, so a crash resumes without duplicates. A batch is ingested newest first, so a reply stored in an earlier batch is found by the reverse lookup of its parent and a reply chain split by a batch boundary stays one thread.
- History progress: `SyncService.historyProgress(userId)` (`history-progress.ts`) returns one `HistoryProgress {accountId, stored, total, state}` per account (`shared/src/domain/history-progress.ts`): `total` sums the server `totalCount` of the counted mailboxes and `stored` the stored rows of the same mailboxes (`countsByMailbox`, capped at each total). Plain IMAP counts every history mailbox (the synced roles of `HISTORY_ROLE_ORDER`); a Gmail account (`labelsMessages`) with an All Mail mailbox takes `total` from All Mail, Spam and Trash and `stored` from the distinct messages (`countDistinct`, by Message-ID header, else `emailId` (X-GM-MSGID), else the row id, so rows stored before `email_id` existed still match their copies) stored in any history mailbox, capped at `total` (`history-count.ts`), because Inbox, Sent and labels are copies of All Mail messages and Spam and Trash are not in All Mail. Counting only the All Mail rows would keep `stored` still while the backfill walks Inbox and Sent first. `state` covers every history mailbox: `state` is `done` once every such mailbox has a finished cursor for its current UIDVALIDITY, `waiting` while none of them has finished its initial sync (slices are skipped as busy then and nothing is downloaded yet), otherwise `running`; without the store it is `[]`. After every slice that was not skipped the engine emits `sync.history` with the account's progress.
- Desktop scheduling (`apps/desktop/src/main/background/history-backfill-scheduler.ts`, one `HistoryAccountLoop` per account, registered in the `PowerAwareLifecycle` next to the sync scheduler, IDLE and due work, reconciled on account events): the first slice runs 10 s after start, `more` chains the next slice after 1.5 s, a busy account is retried after 5 s, a finished history is rechecked after 15 min (60 s while no mailbox has finished its initial sync yet), errors back off exponentially (30 s doubling to 30 min, `backoff.ts`) and throttling errors (OVERQUOTA, bandwidth, too many connections, rate limits, also in an error's `cause`, `throttling-error.ts`) pause for 1 h. The scheduler keeps each account's last step (state, failure count, next due time) in `HistoryHolds` across suspend and resume and across loop recreation, so a resumed loop waits the larger of the start delay and the remaining pause or backoff and keeps counting failures. The loop state (`running`, `idle`, `paused`, `error`) overlays the engine state in `HistoryProgressSource` (`paused` / `error` win unless the history is done) and a change publishes `sync.history` on the hub. IPC `local.sync.history` returns the list, `MailClient.historyProgress()` reads it (Remote `[]`, Demo a running and a finished account from `DemoHistory`, which tests seed and drive through the demo event stream), the renderer keeps it in `useHistoryProgress` (key `['mail','sync','history']`, invalidated by `sync.history`, `account.upserted` and `account.removed`) and Settings → Synchronizácia shows the row "Staršia pošta" in local and demo mode: "Sťahujem históriu: 12 340 z 48 000 správ" (Slovak number grouping) with a progress bar, "Celá história je stiahnutá", "Začnem sťahovať po dokončení prvej synchronizácie" when no unfinished account is running and one is waiting, or "Pozastavené, skúsim znova o chvíľu" when every unfinished account is paused or failing. The renderer handles `threads.changed` at most once per 2 s per account (leading and trailing call, `keyed-throttle.ts`), so a running backfill refetches the loaded thread lists and that account's cached details at a bounded rate.
- Offline window (desktop only): `DeviceSettings.offlineWindow` (`OfflineWindowSchema`: `3m`, `6m` default, `1y`, `5y`, `all`, `shared/src/domain/offline-window.ts`) decides which bodies stay on the device; headers and snippets of all history are always backfilled. `offlineWindowCutoff` turns the window into a cutoff in calendar months (`all` is `null`, keep everything); `monthsBefore` clamps the day to the last day of the destination month, so Aug 31 minus 6 months is Feb 28 (Feb 29 in a leap year) and never rolls over into March. The engine reads it through the optional `OfflineWindowPolicy` port (`cutoff()`, desktop `DeviceOfflineWindow` reads the device settings) and changes bodies through the optional `MessageBodyStore` port (`saveBody`, `evictBefore`, `hydrationCandidates`, `stats`, `newestRemoteDate`; SQLite `sqlite-message-body-store.ts` on `messages_account_body_date_idx`); both are wired only in `local-engine.ts`, so the server keeps every body. Whole-text server search is bounded by the actual body coverage from `MessageBodyStore.newestRemoteDate` (see Server search), and an evicted row is an ordinary `remote` row, so `local.messages.body` serves it through `MessageBodyService` (see On-demand bodies) until a longer window hydrates it again. Hydration (`services/bodies/body-hydrator.ts`) runs at the end of every history slice after the header work, within the same deadline and `shouldYield`: it takes the newest `remote` rows dated at or after the cutoff (at most 50 messages or 10 MB per slice, `offlineBodies` options), plans `fetchUids` batches per mailbox by count and estimated bytes (`hydration-batches.ts`: at most 10 messages and 2 MB of stored attachment sizes per batch, so a large message is fetched on its own; the provider rejects a changed UIDVALIDITY), skips messages estimated above 10 MB (`hydrateMaxMessageBytes`, also checked on the fetched source) for 6 h so they stay `remote` and open from the server on demand, stops before a batch that would cross the byte budget and checks the deadline between batches, verifies the Message-ID, saves text, HTML, snippet and attachments and marks the row `local`. Attachment ids are kept when the parsed parts match the stored list by order, file name and content type, otherwise they are replaced. Every hydrated message journals a quiet thread refresh, so a slice emits exactly one `threads.changed` for the account (the renderer then refetches the lists and the open thread details of that account, so an open thread swaps the snippet for the full body) and never a per-message event. A message the server no longer has, or whose source cannot be parsed or has another Message-ID, is skipped for 6 h (in memory); a fetch error also skips the rest of its batch for 6 h and pauses hydration until the next slice (the report then has `more: false`). A throttling-class failure (`isThrottlingError` in `engine/src/errors/throttling-error.ts`, the same detection `history-cadence.ts` uses) skips nothing and fails the slice with a `ProviderError` carrying the cause, after flushing what was hydrated, so `HistoryBackfillScheduler` enters its 1 h `paused` hold and ignores kicks until it ends. Unfinished hydration keeps the slice report `more` (the report also carries `hydrated`). Eviction (`services/bodies/body-retention.ts`, `EngineServices.bodyRetention.evictDue(userId)`) sets `text_body` and `html_body` to `NULL` and `body_state` to `remote` for local rows dated before the cutoff, in chunks of 200 with a macrotask yield between chunks and at most 10 chunks per tick (about 6 ms per chunk, p95 12 ms on a 50k message database with FTS), then emits `threads.changed` with the number of evicted messages. Rows waiting for a server UID (`uid = 0`, a move without UIDPLUS) are never evicted or hydrated; drafts live in their own table. The FTS triggers re-index an evicted row, so subject, sender and snippet stay searchable while body-only words no longer match. On desktop the due job `body-retention` runs every 30 s, and `OfflineWindowReactor` (a `PowerAwareLifecycle` worker) reacts to a changed `offlineWindow` in `DeviceSettingsStore.onChange` by kicking the history scheduler (`HistoryBackfillScheduler.kick()`, ignored while an account is throttled or backing off after an error, so the `HistoryHolds` cooldowns stay intact) and draining eviction ticks 250 ms apart. IPC `local.sync.offline` returns `OfflineStats {local, remote}` summed over the accounts (`EngineServices.offlineStats`, `MailClient.offlineStats()`, Remote zeros, Demo fixed numbers), invalidated by `sync.history` and `threads.changed`. Settings → Synchronizácia shows the row "Uchovávať offline" in local and demo mode (hidden in remote mode): a segmented control 3 mesiace / 6 mesiacov / 1 rok / 5 rokov / Všetko saved through `settings.device.set`, the description "Staršie maily ostanú v zozname a otvoria sa zo servera. Prílohy sa sťahujú vždy na požiadanie." and "Offline uložené: 8 210 správ" once something is stored.
- Reconciler scale guards (`reconcile-scans.ts`, `sync.reconcile` options): the expunge diff never searches the whole mailbox. It asks the server which stored UIDs still exist (`listUids(path, { among })`: `UID SEARCH UID <set>`, the stored UIDs collapsed into ranges, at most 200 ranges per search), so its cost follows the stored mail, not the mailbox size. Within 6 h of the last diff of that mailbox in this process (the first changed pass after start always diffs) the diff is skipped when `UIDNEXT` and `MESSAGES` both equal the values saved by the previous reconcile (an expunge lowers the count and every arrival raises `UIDNEXT`, RFC 3501 2.3.1.1), or while the mailbox history is complete for the current UIDVALIDITY and the stored UID count equals the server `MESSAGES` count. A full diff becomes due 6 h after the last one (with or without the history store, since the scoped diff is cheap) (or after the mailbox was first seen unchanged in this process), and a due diff forces a reconcile pass even for a CONDSTORE mailbox whose status is unchanged, so an expunge masked by an equal count is removed at the latest 6 h later. Without CONDSTORE the flag pass no longer fetches `1:*` once a mailbox stores more than 4000 UIDs: each pass fetches the newest 2000 stored UIDs plus a 2000-UID slice of the older ones whose offset rotates per pass, so every stored UID is rescanned within `ceil(older / 2000)` passes. The offset is persisted in `history_backfill.flag_scan_offset` (SQLite migration `0030`, kept when the cursor is saved, only for mailboxes with a history cursor), so coverage continues across restarts; without a cursor row it lives in memory and starts at 0. Label rescans keep scanning every stored UID.
- On-demand bodies (`services/bodies`): `MessageBodyService.get(userId, messageId)` returns `MessageBodyResult` (`shared/src/domain/message-body.ts`): `{ status: 'local', textBody, htmlBody }` for a stored body, `{ status: 'ok', textBody, htmlBody }` for a body read from another stored copy or from the server, `{ status: 'offline' }` when the server cannot be reached and `{ status: 'gone' }` when no copy has it any more. For a remote row it first uses another stored copy with a body (same email id, else same Message-ID), so an INBOX copy serves an old archived one even offline; otherwise it fetches the full source with `fetchMessage` (the row, then up to 3 other remote copies), parses it with the normal `MessageParser` and drops a source whose Message-ID differs from the stored one (a reused UID after a UIDVALIDITY change). Concurrent requests for one message share one fetch. Fetched bodies are never written to the store; they live in `RemoteBodyCache`, an LRU of at most 20 MB (2 bytes per UTF-16 code unit of text and HTML) and 100 entries with a 10 minute TTL (`options.bodies`). Reads go through `LingeringSessions` (`services/shared/lingering-sessions.ts`, `EngineServices.readSessions`): one connected provider per account, its work serialized, closed after 60 s idle by a sweep on the `IntervalTimer` that runs only while a session is open, dropped after any failed operation (the next request reconnects), closed when the account is updated or removed and, on the desktop, at shutdown. Received attachments of a remote row are taken by index only when the full parse has the same filename and content type at that index, otherwise by the first attachment with that filename and content type (`AttachmentExtractor.extractAll`), because the stored list came from BODYSTRUCTURE. AI and MCP tools keep reading the stored body, so they see only the snippet of a remote message. Server rows are always local, so the server never fetches.
- Server search (`services/search`, desktop only through IPC `local.search.server`): `ServerSearchService.search(userId, ServerSearchRequest)` returns `ServerSearchResponse {requestId, status: ok|partial|offline|skipped|unsupported, hits: [{thread, messageId, date}]}` (zod schemas in `shared/src/api/endpoints/search.ts`). The query is split on whitespace into at most 8 terms that must all match (`searchField` `from` / `subject` narrows them to the sender or the subject). Per account `AccountSearchPlanner` picks the mailboxes with a completed initial sync (`search-mailboxes.ts`: Gmail only All Mail; IMAP inbox, archive, sent, then custom folders as selected for sync, never trash or spam, at most 12) and `search-plan.ts` decides: when the history backfill of the account is complete (every history mailbox cursor done under the current UIDVALIDITY), `from` / `subject` searches are skipped because local search already covers every stored header, a whole-text search (`remote-bodies.ts`) is skipped when the optional `MessageBodyStore` reports no `remote` row for the account (`newestRemoteDate` null) and otherwise bounded with `before` = the UTC day of the newest `remote` row plus 2 days (one day of margin for the server time zone), so bodies not hydrated yet after a window change and oversized bodies that are never hydrated stay searchable; without the store or before the history is complete the server is searched without a date bound. Each mailbox is searched through `LingeringSessions` (one step per mailbox, so body reads of the same account interleave) with `MailProvider.searchText`, newest 50 UIDs per mailbox. UIDs are mapped to stored rows by the optional `MessageUidLookup` port (`findByUids`, SQLite, wired in `local-engine.ts`), else `findByLocation`. Unknown UIDs up to the mailbox `lastUid` are read with `fetchSummaries` and stored as quiet header-only `remote` rows (`ingestSummary`, quiet `thread-refresh` work flushed by `flushThreads`, one `threads.changed`); UIDs above `lastUid` are left to the next sync so new mail keeps its body, notifications and effects. That ingest runs as an exclusive run of the account in `AccountRunQueue` (shared by `SyncService` and the search): it waits for a running sync or history slice, a history slice yields to it after the current batch, and a sync requested meanwhile runs after it. Hits keep one entry per thread (the newest matching message), drop trash and spam threads, apply `unread` (thread) and `hasAttachment` (non-inline attachment on the hit message) and are sorted newest first. Searches are latest-wins per user: a newer search makes the older one stop between steps and answer `skipped` with no hits; a mailbox step that waited for the account session checks again after it gets the session and skips the SEARCH when the search was replaced or its deadline passed. Found UIDs are resolved against the UIDVALIDITY the SEARCH ran under: when the stored sync state of the mailbox has another UIDVALIDITY by then (a concurrent rebuild), the mailbox adds no hits and the answer is `partial`. After 8 s (`options.search.deadlineMs`, a one-shot on the `IntervalTimer`) the hits found so far are returned as `partial`; a mailbox that fails while the server stays reachable, a UIDVALIDITY change or a rejected search also make the answer `partial`; when the first mailbox of every searched account cannot reach the server the answer is `offline`; when every account was skipped it is `skipped`. Opening a hit is a normal `local.threads.get` and its body comes from `local.messages.body`. `LocalMailClient.searchServer` calls the IPC channel; `RemoteMailClient` answers `unsupported` (`data/server-search.ts`) and `DemoMailClient` simulates the search (see the search palette).
- Threading also looks backwards: when no stored message has one of the new message's ids (Message-ID, In-Reply-To, References), `MessageRepository.findThreadIdByReplyTo` finds the oldest stored message whose `In-Reply-To` is one of them, so a parent stored after its reply, or a sibling of a reply whose parent is missing, joins the existing thread before the subject fallback runs. SQLite serves it from `messages_account_reply_idx (account_id, in_reply_to)`, Postgres from `messages_account_reply_hash_idx (account_id, md5(in_reply_to))` (migration `0029`), because a long In-Reply-To may exceed the B-tree entry size.
- A copy ingested from the spam mailbox never counts as an inbox arrival, so it triggers no automations, AI one-liners or notifications, and it creates no Jira tasks or calendar invitations. An INBOX copy of the same message is classified on its own.

## Messages and placements

Target model, rolled out in slices (see "Rollout" below). Until a slice lands, the older text in this document describes the code in main.

A **message** is one logical mail: headers, bodies, snippet, flags, labels, attachments, thread. A **placement** is one copy of it on the IMAP server: a mailbox and a UID. Sync, actions and expunge work on placements. Thread detail, thread lists, search, AI, MCP, automations, Jira events and calendar invites work on messages.

Two principles keep the change safe:

- Provider commands stay the ones Relay sends today (archive = MOVE INBOX -> All Mail, trash = MOVE -> Trash, X-GM-LABELS STORE for labels, ...). Only the local bookkeeping changes from rows to placements.
- Local placements after an action are optimistic. Sync reconciles them: the expunge diff removes placements the server no longer has, and ingest adds the ones it gained. A wrong guess about Gmail semantics self-corrects on the next pass instead of losing mail.

### Tables (both stores)

- `messages`: one row per logical message. `seen`, `flagged`, `answered`, `body_state`, `headers`, `attachments`, `email_id` (text, lossless X-GM-MSGID) stay here. `mailbox_id` and `uid` stay until the last slice as the **primary placement** mirror (see `placementRank` below), written only by the message repository, with their unique index unchanged. The last slice drops them.
- New `effects_at` on `messages` (nullable timestamp): when the creation effects (Jira event, calendar invite) were queued. The migration sets it on every existing row.
- `message_placements (message_id, mailbox_id, uid)`:
  - `message_id` FK `messages.id` ON DELETE CASCADE, `mailbox_id` FK `mailboxes.id` ON DELETE CASCADE.
  - Primary key `(message_id, mailbox_id)`: a message is at most once in a mailbox. A pending placement is addressed by this key.
  - Unique `(mailbox_id, uid) WHERE uid > 0`. `uid = 0` (`PENDING_UID`) is a placement whose UID is not known yet (MOVE or APPEND without COPYUID / APPENDUID). UID lists, UID scans and counts only see `uid > 0`.
  - Folder views join placements to messages by `message_id`. A denormalized `thread_id` is added only if the scale measurements ask for it.
- `message_aliases (alias_id PK, message_id FK messages CASCADE)`: ids of messages merged into another one. Every repository method that takes a message id (reads and writes, including draft ownership checks) resolves an alias first, so ids held by the renderer, undo snapshots, pending work and JSON keep working after a merge.
- `message_labels`, SQLite `messages_fts` (triggers on `messages`) and Postgres `search_vector` stay per message. FTS and `search_vector` therefore hold each Gmail message once.

Invariant: every message has at least one placement. The message repository is the only writer of placements and deletes a message in the same transaction that removes its last placement.

### Identity rule

- Label-based accounts (`labelsMessages(account)`: Gmail OAuth, or IMAP on `imap.gmail.com` / `imap.googlemail.com`): the logical message is `(account_id, email_id)` (X-GM-MSGID). A copy in INBOX, All Mail, Sent or a label mailbox is a placement of that one message. Two placements join only on an equal, non-null `email_id` reported by the server.
- When several legacy messages (not merged yet) share the fetched `email_id`, the placement goes to the keeper chosen by the merge rule below.
- The only Message-ID match is the adoption of a placeholder Relay created itself (its Message-ID was generated by Relay): a `PENDING_UID` placement, or a Sent message recorded after SMTP without `email_id`, in the same mailbox, with exactly one candidate. The adopting copy fills `email_id`. Everything else with a null `email_id` stays its own message until the migration resolves it from the server (see below).
- Generic IMAP: a copy in two folders is two messages with their own flags and keyword labels. Every message has exactly one placement. A `PENDING_UID` placement is adopted in the same mailbox by Message-ID with exactly one candidate, as today.

### Flags and labels

- Gmail: `\Seen`, `\Flagged`, `\Answered` and X-GM-LABELS are per message on the server and stored once on the message. A flag refresh from any placement writes the message, and a pending provider op for that message wins over it (`synced-flags`, as today). Gmail reports a flag change in every mailbox that holds the message (CONDSTORE per mailbox), so both refreshes write the same value.
- Generic IMAP: flags and keyword labels are per copy on the server, and a copy is its own message, so storing them on the message stays exact.
- Mailbox unread counts stay server totals from STATUS, with optimistic local deltas between refreshes: a flag flip adjusts every mailbox the message has a placement in, and adding or removing a placement of an unseen message adjusts that mailbox.

### Sync ingest

One repository operation, `MessageRepository.place(...)`, used by full ingest, summary ingest (history backfill, server search hits) and the Sent recorder. In one transaction it either refreshes, attaches or creates. On Postgres it takes `pg_advisory_xact_lock` on `(account_id, email_id)`, so a concurrent Sent recorder and sync cannot create the same Gmail message twice. SQLite writes are already serialized. For each fetched `(mailbox, uid)`:

1. A placement at that location exists: refresh the message (flags, labels, a missing `email_id`). Done.
2. Label-based account and a message with that `email_id` exists: add the placement, or adopt that message's `PENDING_UID` placement in this mailbox. Then refresh flags and labels and journal a thread refresh with the placement's role. The body, thread, Jira classification, split match, calendar parts and attachment ids are not computed again. A remote (header-only) body is filled when this fetch carries the full source.
3. Placeholder adoption by Message-ID (identity rule above).
4. Otherwise create the message and its first placement (thread resolution, labels, Jira, splits, calendar parts, as today).

Fetching stays as today: the full source per new UID. The initial sync keeps its order (#121): inbox windows first, the newest `firstBatchSize` with their parents flushed before the backlog. The only change is that an All Mail copy of a stored message becomes a placement instead of a second row. Skipping that download (a header fetch of X-GM-MSGID before the source) is a later optimization, taken only if the measurements of slice c call for it.

Effects:

- Arrival (notifications, AI one-liners, live automations): a placement added in the inbox mailbox by a live incremental fetch, when the message had no inbox placement before. Adopting a pending placement that a local action created (undo, restore) is not an arrival. Refetches after a UIDVALIDITY reset and the initial sync are not live, as today. Automation claims stay keyed by message id, so a message re-inboxed on the Gmail web runs a rule at most once (today it got a new row and ran again).
- Jira events and calendar invites: any live or backlog `place(...)` (refresh, attach or create) queues them when `effects_at` is null and the placement's role accepts them, then sets `effects_at`. History and search summary ingest leave `effects_at` null, so the first full ingest of such a message still queues them. One column covers both effects; their role sets differ only for drafts.
- New UIDs: a message that comes back into a mailbox (restore, re-inbox on the web) gets a new UID above the mailbox's last UID, so incremental fetch finds it. Optimistic `PENDING_UID` placements are replaced by the UID sync reports; COPYUID UIDs come from the server.

### Expunge, UIDVALIDITY and vanished mailboxes

- `deleteByUids(mailboxId, uids)` takes positive UIDs. It deletes those placements, deletes the messages left without a placement and returns the threads of both, so thread state is refreshed (a Gmail thread whose INBOX placement is gone becomes done while its All Mail placement keeps it alive, the #121 invariant).
- `removePlacement(messageId, mailboxId)` cancels one placement, pending or not, with the same last-placement rule.
- `forgetMailbox(mailboxId)` removes every placement of a vanished or deleted mailbox, pending ones included, through the same rule, before the mailbox row goes. So the ON DELETE CASCADE on `mailbox_id` never leaves a message without a placement. Account deletion cascades messages and placements together.
- UIDVALIDITY change: every placement of the mailbox is dropped, as rows are today. On Gmail a message survives through its All Mail placement (when All Mail is shown in IMAP; otherwise it behaves as today), and the refetch re-attaches it by `email_id`. UID cursors of that mailbox (body repair, invite backfill, calendar rebuild) restart from 0, as today.

### Actions on placements

Actions load the thread's messages with their placements and pick placements, not messages. `placementRank` orders the placements of a message: a real UID before `PENDING_UID`, then inbox, archive, label, custom, sent, spam, trash. The first one is the primary placement.

- Read, unread and pin: one local write per message. Provider op: one `STORE` on the primary placement (Gmail shares the flag across mailboxes; generic messages have one placement).
- Gmail labels: one local label write per message. Provider op: `X-GM-LABELS` on one carrier placement (All Mail first, as `labelCarriers` today).
- Provider ops that move name their source placement (`mailboxId`, `uid`) in the payload and in their ref (`<messageId>:move:<sourceMailboxId>`), so a message with several placements moves only that copy and two moves of different copies never collide.
- Archive / Done (Gmail): MOVE the INBOX placement to All Mail, as today. Locally the INBOX placement is removed. The All Mail placement is kept, or added at the COPYUID UID. No row merge and no row move. Generic IMAP: MOVE the placement and rewrite its mailbox and UID (`PENDING_UID` until COPYUID or sync).
- Undone (Gmail): the same MOVE All Mail -> INBOX as today. Locally an INBOX placement is added (COPYUID UID or pending) and the All Mail placement is kept. If Gmail did drop it, the expunge diff removes it. Today the All Mail row itself is moved and lost locally.
- Move to a Gmail label mailbox: the same commands as today. Locally the label goes on the message and the INBOX placement is removed.
- Trash and spam (Gmail): the same MOVE of one received placement as today. Locally the moved placement becomes the Trash / Spam placement. The others stay until the expunge diff confirms what Gmail removed. Restore: MOVE back to the origin mailbox. The returning All Mail placement is attached by `email_id` during sync.
- Trash, spam and move origins stay keyed by message id and keep their payload (source mailbox, label they added, held origins, the `markedDone` and revision data undo checks), plus the source placement UID.
- Thread roles come from placements, after applying pending moves to the placements they name. `MailCopies.filedRoles` becomes: the archive placement of a message that also has a sent placement counts as sent, unless the message is addressed to the account itself.
- Folder deletion (`trashed-copies`) moves the folder's placements to Trash with the same transition as the trash action.
- `MovedCopyMerger`: on a label-based account the twin is the same message, so the merge is replaced by a placement update. On generic IMAP, when a verified COPYUID target `(mailbox, uid)` already belongs to another message (sync ingested the target first), the two messages are merged with the same `MessageMerges` port the migration uses.

### Read side

- `listByThread` returns logical messages with their `placements`. Thread detail, AI requests, MCP `get_thread`, thread summary counts and participants therefore contain each Gmail message once.
- Generic IMAP copies are separate messages in thread detail and in counts alike. Today counts collapse them by Message-ID while detail shows both. The last slice removes that collapse, so a mail sent to oneself counts as its Sent and Inbox messages.
- `Message` gains `placements: { mailboxId, uid }[]` in `shared` (HTTP and IPC). `mailboxId` and `uid` stay on the wire as the primary placement until the last slice, which keeps API version 1 compatible.
- Search hits map UIDs through placements to the logical message. Folder views filter threads by placements of the mailbox.
- Bodies and attachments: fetched from the primary placement with a real UID, then the other placements on a missing UID or a UIDVALIDITY mismatch. Hydration and body repair work per message (one download per message). Body repair and invite backfill keep their `(mailboxId, afterUid)` cursors over placements.
- History progress counts messages that have a placement in the counted mailboxes, on both sides of the fraction.

### Message ids stay stable

- A message's id never changes while it gains or loses placements.
- A merge keeps one id (the keeper) and turns the others into aliases. Keeper id: an inbox placement first, then the oldest row (SQLite `seq`, Postgres lowest `id` as a deterministic tiebreak).
- Merged content: the most complete body among the group (`local` over `remote`, then the longer text), with its headers and attachment metadata.
- Merged flags and labels: the keeper's values, overridden by any pending provider op of a group member. A flag and label rescan of the account's Gmail mailboxes is queued, so the next sync restores server truth. No OR or union of stale values.
- Received attachment ids of losers are not kept. Forwarding copies attachments into the draft store, so only open views hold them. Each merged chunk publishes `thread.upserted` for its threads, so clients refetch detail.

### Merging existing duplicates (migration)

1. Schema migration (SQL, one transaction): create `message_placements` and `message_aliases`, add `messages.effects_at` (set to now on every row), `INSERT ... SELECT` one placement per existing message. The `(mailbox_id, uid)` unique index on `messages` stays. This ships in slice a, and nothing is enqueued yet.
2. Slice d's migration enqueues one `pending_work` row `kind = 'copy-merge'` per account. The engine `CopyMergeBackfill` runs it inside the account's sync, after the mailbox passes (so the expunge diff has removed stale locations first), on desktop and server alike. The sync of an account is already serialized (desktop serial queue, server pg-boss singleton per account).
   - Accounts that are not label-based drop their work row.
   - Resolve: for messages with a null `email_id` and a positive UID, `UID FETCH <uids> (X-GM-MSGID)` per mailbox (UIDVALIDITY checked) fills `email_id`. Rows the server no longer has are left to the expunge diff, and unresolved rows stay separate.
   - Merge: keyset over `(account_id, email_id)` with chunks bounded to 500 messages (`MessageMerges.nextGroups`). Each chunk is merged in its own transaction (`MessageMerges.merge`), and the affected threads are queued for a refresh.
   - Skipped groups, left separate and counted in the report: groups that span threads (permanent), and groups with two positive UIDs in one mailbox (a stale location the reconciler removes, so a later sync merges them).
   - A group larger than the chunk is merged alone in its own transaction.
   - It is idempotent (a group with one message is not a group) and resumable. The work row stays until a pass finds no mergeable group and no same-mailbox conflict. Then it is retired.
3. `MessageMerges.merge` re-reads each group under a write lock (SQLite `BEGIN IMMEDIATE`, Postgres `FOR UPDATE` on the group's rows), builds `loser_id -> keeper_id` and then, before deleting anything (Postgres cascades `automation_runs` and sets `drafts.in_reply_to_message_id` to null on delete):
   - placements: per mailbox, at most one placement survives. A positive UID wins over `PENDING_UID`, and of several pending ones the keeper's wins. The rest are deleted, then the survivors are moved to the keeper.
   - `message_labels` and `automation_runs`: insert-or-ignore onto the keeper.
   - `drafts.in_reply_to_message_id`, `calendar_events.message_id`, `ai_results.source_message_id` and `automation_activity.message_id`: update.
   - `ai_jobs.source_message_id`: update, except rows whose remap would collide in the active-job unique index. Those keep the loser id, which the alias resolves.
   - Message ids inside JSON (`ai_jobs.input`, `ai_results.output`, `automation_activity.actions`, `pending_work.payload`): rewritten through typed JSON paths in rows that contain a loser id, with duplicate ids in arrays removed.
   - `pending_work.ref`: rewritten, with one reducer per kind on a primary key clash:
     - `provider-op`: flag and label ops, the later `updated_at` wins (the latest user intent). A loser's move op gets the loser's placement as its source, and so its own ref, and never collides.
     - trash, spam and move origins: the later `updated_at` wins.
     - `message-effects`: one row, `arrival` OR-ed.
     - `jira-event`, `calendar-invite`, `calendar-rebuild-part`: one row, with the keeper's payload (the content is the same message).
   - The keeper takes the merged fields. Aliases are inserted, and older aliases of a loser are re-pointed to the keeper.
   - The losers are deleted. The FTS delete trigger and the Postgres generated column clean up search, and FTS needs no rebuild.

### Dropping the old columns (last slice)

- Postgres: `ALTER TABLE messages DROP COLUMN mailbox_id, DROP COLUMN uid`.
- SQLite cannot drop an FK column, and the drizzle migrator runs every pending migration in one transaction with foreign keys on, where a table rebuild would cascade-delete `message_labels` and placements.
- So the rebuild is a separate step in `migrate()`, after the drizzle migrations, idempotent (it runs only while the column exists). It runs on the startup connection with `PRAGMA foreign_keys=OFF` set before `BEGIN`.
- Inside one transaction it:
  - creates the new table and copies the rows with their `seq` (the FTS rowid; `seq` is a plain rowid, so new rows continue after the max);
  - drops the old table and renames the new one;
  - recreates indexes and FTS triggers;
  - runs `PRAGMA foreign_key_check` and rolls back if it returns a row.
- `PRAGMA foreign_keys=ON` is restored in `finally`. It is tested on upgrades from before slice a and from slice d.

## Task systems

External task systems are read-only views of the user's own open tickets next to the mail ("Task systémy"). Providers are `jira`, `linear` and `github` (`TaskSystemProviderSchema`, `shared/src/domain/task-system.ts`), all available (`AVAILABLE_TASK_SYSTEM_PROVIDERS`); the connect input and the stored credentials are discriminated unions by provider (Jira: site + e-mail + API token, Linear: `apiKey`, GitHub: `token`) and adapters narrow them with `isCredentialsOf`. A `TaskSystemConnection` (id, user, provider, label, normalized site URL, account name, status `ok` | `error`, `lastError`) never carries secrets; the stores also keep the provider's account id (`TaskSystemConnectionRecord.externalAccountId`) so connecting the same site and account again updates the existing connection (that is how "Znova pripojiť" works). The credentials (`TaskSystemCredentials`) live behind `TaskSystemSecretStore`: every call takes the owner's `UserId`; the server encrypts them with AES-256-GCM into `task_system_connections.credentials_envelope` and reads and writes it only by owner and connection id (associated data `relay:task-system:<userId>:<id>`), the desktop keeps them under `<userId>/<id>` in the `task-systems` namespace of the Electron `safeStorage` secret file. The stores upsert a connection on its account key (owner, provider, site, account id), so two first connects of the same account racing each other end up on one row. Tickets are never persisted: `TaskSystemService.listTasks` asks the adapter live and returns `ExternalTaskList {items, truncated}` (`ExternalTask`: key, title, url, status name + category `todo` | `inProgress` | `done`, `TaskPriority`, project, due date, updated). `connect` verifies the credentials first and stores nothing on failure; it then writes the secret before the row is marked `ok` (a new connection is first stored as `error` with "Chýbajú prihlasovacie údaje" and removed again when the secret cannot be stored). A rejected token (`ReauthorizationRequiredError` from the adapter, only HTTP 401) becomes `ForbiddenError` and marks the connection `error`, but only while the credentials used for that request are still the stored ones, so a list that started before a reconnect cannot break the new token; a later successful list marks it `ok` again. Other failures (including 403, "Účet nemá v Jira prístup k vyhľadávaniu úloh") are `ProviderError` and leave the status alone; `disconnect` deletes the row and then the secret. Connect, disconnect and status changes emit `taskSystems.updated {connectionId}`. Contract: `GET/POST /task-systems/connections`, `DELETE /task-systems/connections/:id`, `GET /task-systems/connections/:id/tasks` and IPC `local.taskSystems.list|connect|disconnect|tasks`; tables `task_system_connections` (SQLite `0036`, Postgres `0035`). `@relay/task-systems` holds the adapters and `createTaskSystemRegistry` (Strategy per provider behind `StaticTaskSystemRegistry`). `JiraCloudAdapter` uses Basic auth and verifies with `GET /rest/api/3/myself` on the site; when that answers 401 it reads the cloud id from `{site}/_edge/tenant_info` and retries through the fixed gateway `https://api.atlassian.com/ex/jira/{cloudId}` (scoped API tokens work only there). The route that worked is stored in the non-secret part of the credentials (`route: site | gateway`) and used for listing, and a `maxResults: 1` search at connect time makes a token that cannot search fail right away. It lists with `POST /rest/api/3/search/jql` (`assignee = currentUser() AND statusCategory != Done ORDER BY priority DESC, updated DESC`, 100 per page while Jira returns a `nextPageToken`, also after an empty page, at most 300 issues and 10 requests, stopping on a repeated token; a hit bound sets `truncated`), drops an invalid due date to `null`, validates every response with zod, maps `statusCategory.key` (`new`, `indeterminate`, `done`) and the priority name (Highest/Blocker/Critical urgent, High/Major high, Medium, Low/Lowest/Minor/Trivial low, anything else none) and links `{site}/browse/{key}`. Because the server fetches user supplied URLs, `AtlassianSitePolicy` allows only `https://<name>.atlassian.net` or `<name>.jira.com` without credentials or port, normalized to the origin, and requests never follow redirects; tests inject a loopback policy and point the adapter at the Jira stub in `@relay/config/test-infra`. `connectRequestOf` builds the adapter access per provider through a mapped type keyed by provider; Linear and GitHub have no user supplied URL, so the connect step passes the public site (`https://linear.app`, `https://github.com`) and each adapter talks only to its fixed API origin (overridable only in code, for the stubs). The adapter returns the connection's `siteUrl` and `defaultLabel` (Jira: host name, Linear: organization name, GitHub: login). `LinearAdapter` sends the personal API key as `Authorization: <key>` to `https://api.linear.app/graphql`, verifies with `viewer` + `organization` plus a one item `assignedIssues` (`siteUrl` `https://linear.app/<urlKey>`) and lists `viewer.assignedIssues` without `completed`/`canceled` states, ordered by `updatedAt`, 100 per page over `endCursor`, at most 300 issues and 10 requests, stopping on a repeated cursor; priority 1-4 maps to urgent/high/medium/low (0 none), `state.type` started is in progress, completed/canceled done, the rest todo, project falls back to the team. HTTP 401 and GraphQL `AUTHENTICATION_ERROR` are rejected credentials, 403/`FORBIDDEN` an access-denied `ProviderError`, `RATELIMITED` a `RateLimitedError` (`rate_limited`, HTTP 429, keeps the status and the renderer does not retry it). `GitHubIssuesAdapter` uses `Authorization: Bearer <token>` with `X-GitHub-Api-Version: 2022-11-28` against `https://api.github.com`, verifies with `GET /user` plus a one item issue list and lists `GET /issues?filter=assigned&state=open&sort=updated` following `Link rel="next"` only on the API origin (300 issues or 10 pages), skips pull requests, keys issues `owner/repo#number`, reads the due date from the milestone and maps labels (first match of `priority: urgent|critical|p0`, `high|p1`, `medium|p2`, `low|p3|p4` with `:`, `/` or `-`, or bare `P0`-`P4`; `in progress`/`doing` makes the issue in progress); only 401 means rejected credentials; 429, a 403 with `x-ratelimit-remaining: 0` or a secondary rate limit message is a `RateLimitedError`, any other 403 an access-denied `ProviderError`. The `Link` header is parsed quote and bracket aware and `next` is resolved against the request URL before the same-origin check. Stubs: `startLinearStub` and `startGitHubStub` next to the Jira stub.

## AI (`@relay/ai`)

- `AiRunner` port: `run(request: AiRequest): AsyncIterable<AiEvent>` (`AiEvent` is defined in `shared` so it can be streamed over IPC unchanged). Implementations: `ClaudeCodeRunner` (`claude -p --output-format stream-json`) and `CodexRunner` (`codex exec --json`), each spawning the CLI with a mail MCP server attached.
- Runner location is a user setting: `server` (server AI worker uses the CLIs installed on the server) or `local` (the desktop main process uses the CLIs installed on this machine). Like T3 Code environments.
- `CliDetector` reports which CLIs are installed and logged in on the current machine, shown in Settings → AI.
- Tasks: one-line summary, thread summary + checklist, reply suggestions, rewrite draft, free-form chat over mail, create task from mail, automation task verdict (`automationTask`), automation reply draft (`automationDraft`, one reply body for the triggering message), rule suggestion (`ruleSuggest`, a draft automation rule from a sentence, see below). Jobs can carry a per-job model and effort that the CLI dialects pass on (`--model`, Claude `--effort`, Codex `-c model_reasoning_effort`).
- Rule suggestion (`ruleSuggest`, "Opíš pravidlo vlastnými slovami"): the job input is the user's sentence (at most 500 characters), the editor's account (or `null`) and a catalog of every account with its labels and move targets (ids and names, `RuleSuggestRequestSchema` in `shared/src/domain/rule-suggestion.ts`, built by the renderer from the labels and `moveTargetsOf` of each account). It runs like every other user-triggered job: `ai.run` IPC on the local engine in local mode, a server job in synced mode (the server AI worker, or the desktop worker when the user runs AI locally). The prompt (`specs/rule-suggest.ts`, no mail tools) wraps the sentence and the catalog as untrusted data and shows the model only names, never label or mailbox ids. The model answers `RuleProposalSchema` (`shared/src/domain/rule-proposal.ts`: the existing condition types, actions with label and folder names instead of ids, `understood` and `unmapped`); anything else is repaired once and then fails as `invalid_output`, which the editor shows as "AI nevrátila platný návrh pravidla. Skús pravidlo opísať inak." `resolveRuleProposal` (shared, called from the spec's `toOutput` and by the demo client) turns it into a `RuleSuggestion`. Action authorization is deterministic and reads only the sentence (`ruleIntent`, `rule-intent.ts`) with a few clause rules. (1) Masking: curly apostrophes count as straight ones, addresses ("Meno <adresa>" is one address; the display name never takes an address, a negation or a joint), quoted text and condition phrases are removed first: conditional clauses ("if", "when", "ak", "keď", "pokiaľ" up to a comma, a sentence end or "then"/"tak"/"potom"), sender ("od X", "from X", "z domény X"), recipient ("sent to X", "CC'd to X", "v kópii X", "adresované na X", "pre X"), folder ("z priečinka X"), attachment ("s prílohou", "bez prílohy") and subject ("predmet obsahuje X", "subject contains X"; a quoted value is taken whole, an unquoted one up to a comma, a semicolon, the end of its sentence, "then"/"potom"/"tak", or "a"/"and" followed by an action word). (2) Clauses and phrases: the rest is split into clauses at punctuation and "ale"/"but", uncertain clauses ("možno", "maybe", a question) are skipped, and every Slovak or English keyword of an action type (archivuj/archive, presuň/move, označ ako prečítané/mark read, pripni/pin, štítok/label, pripomeň/remind, notifikácia/notify, úloha/task, zhrnutie/summary, odpoveď/reply, prepošli/forward; a bare "draft" or "koncept" is no reply) opens a phrase that runs to the next keyword, to "then"/"potom"/"tak", or to "a"/"and"/"plus" when an action word follows within three words. (3) Negation: "nie", "nikdy", "not", "don't", "bez", "without", "no" deny every phrase after them up to the clause end or "then"/"potom"/"tak" (Slovak "ne-" verbs never match). (4) Names: after a label or folder keyword every word up to the phrase end or a negation is the name, action words included, and the name (quoted text whole, fillers like "to", "do", "folder" trimmed) belongs only to that action. Every other proposed action is dropped and listed as "… (veta to nežiada)", whatever the model or the catalog said. A label or folder is resolved from the name the user said in its own phrase (a quoted name only as the whole catalog name; otherwise the whole catalog path first, then a path suffix, then a common stem, then the catalog name whose words the phrase contains), and the proposed name must agree with that result (otherwise "veta ho nemenuje"). (5) Forwarding: `forward` needs exactly one recipient candidate in its phrase, the address after "to", "na", "on", "at" or "komu"; senders and recipient conditions are no candidates, and a phrase with more candidates forwards nowhere. The address must also pass the email schema. The account is the one the model named from the catalog, else the editor's account, else the only account whose labels and folders hold every named target (or the only account). Label and folder names are matched in code ignoring case, diacritics and spacing; a match must be unique (two names that fold to the same key are "nejednoznačný názov"), a qualified path ("Projekty/Alfa") matches only that path or a path ending with it and never another folder with the same leaf, and a bare name falls back to a unique common stem, so "faktúry" finds "Faktúra". Unresolved or account-less targets are dropped and listed in `unmapped`; duplicates, a second placement action and regular expressions that do not compile are dropped. The name follows the strongest condition like "Vytvoriť pravidlo z mailu" (sender address, domain, subject text, as written), else the model's name. The editor applies a suggestion as an unsaved draft (`applySuggestion` keeps the AI settings, `enabled` and the order; when no action survived the actions stay empty, the note says "Akcie z vety som nerozpoznal" and the rule cannot be saved until the user picks one, since `isComplete` needs a condition and an action) and shows "Rozumiem: … Nepodarilo sa priradiť: …" under the bar; the summary and the live preview follow the draft. A proposal is applied to the latest state of the rule, and only when its name, account, criteria and actions did not change while the AI worked, a condition edit or a rule name that is still being typed counts, invalid values included (otherwise "Pravidlo sa medzitým zmenilo, návrh som nepoužil."); leaving the editor cancels a pending run, and the bar sends nothing until the labels and folders of every account are loaded. The bar sits at the top of the rule editor, on the templates screen ("+ Nové pravidlo") and behind "Opíš nové pravidlo…" in the list; the last two create a new unsaved draft. On a saved rule the proposal is staged (header "Neuložené", "Uložiť pravidlo" and "Zahodiť návrh", no apply to existing mail) and leaving the editor discards it. Nothing is saved without "Uložiť pravidlo" (refused while a condition or exception row is unfinished or pending; a proposal that arrives during the save stays as the new draft): later edits of a proposal stay in the draft, while other rules keep saving each complete edit. The demo client answers with a small deterministic parser (`data/demo/demo-rule-parser.ts`: "od", "z domény", "predmet", "príloha", "archivuj", "označ ako prečítané", "pripni", "štítok X", "presuň do X", "pripomeň o N dní", "okrem" outside quotes; "bez prílohy" and a subject over 200 characters are reported as unmapped) followed by the same resolver.
- Safety: the agent gets read-only mail tools plus `create_task`/`create_draft`. Sending always needs explicit user confirmation in the UI. Email content is untrusted input (prompt injection).

## Mail providers (`@relay/mail-core`)

- `ImapMailProvider` (imapflow): folders (list, create, rename, delete), incremental fetch by UID/MODSEQ, IDLE, flags, keywords (written exactly as given, purge over `1:*`), Gmail labels, move, append.
- Message summaries (`MailProvider.fetchSummaries(path, uidValidity, uids)`, `imap/fetch-summaries.ts`) read a message without its full source, for header-only history rows: batches of 100 UIDs, one `UID FETCH` of flags, INTERNALDATE, RFC822.SIZE, X-GM-LABELS / X-GM-MSGID, BODYSTRUCTURE and `BODY.PEEK[HEADER]`, then one partial fetch `BODY.PEEK[<part>]<0.4096>` per preview part. The header block drops the trace headers listed in the engine's `TRACE_HEADERS` (Received, DKIM, ARC, Authentication-Results, ..., applied by `parser/trace-headers.ts`) locally, because imapflow cannot send `HEADER.FIELDS.NOT`. `summary-structure.ts` picks the preview part (first inline text/plain, else text/html, never inside an embedded message) and lists attachments from BODYSTRUCTURE with mailparser's rules and order (disposition, related cid parts, calendar body parts, `message/rfc822` descended only when inline), so the index of an attachment matches the full parse used for on-demand downloads; sizes are estimates. `summary-preview.ts` decodes the truncated part (complete base64 quanta, no dangling quoted-printable escape, charset via TextDecoder) and builds the snippet with the same `buildSnippet`. The snippet equals the full-parse snippet, except that text after the first text part (more text parts, inline embedded messages) is not included. `listUids(path, { range: { from, to } })` runs `UID SEARCH UID from:to`, `{ among: uids }` runs `UID SEARCH UID <set>` in batches of 200 ranges and `{ newest: n }` runs a NOOP and `UID SEARCH <exists-n+1>:<exists>` (GreenMail rejects `*` in a sequence search key), falling back to `UID SEARCH ALL` when the answer is rejected or does not cover the whole range (a stale `EXISTS`).
- Text search (`MailProvider.searchText(path, uidValidity, {terms, field, before?, limit})` -> `{uids, complete}`, `imap/search-text.ts`) checks UIDVALIDITY, answers an empty mailbox without a command and returns the newest `limit` UIDs. Gmail (`X-GM-EXT-1`) uses one `X-GM-RAW` query (`imap/gmail-raw-query.ts`: every term quoted with `\` and `"` escaped, `from:` / `subject:` prefixes, `before:YYYY/MM/DD`) through imapflow `gmraw`, which adds `CHARSET UTF-8` for non-ASCII. Plain IMAP sends `UID SEARCH [CHARSET UTF-8] TEXT|FROM|SUBJECT <term> ... [BEFORE dd-Mon-yyyy]` built by `imap-search-attributes.ts`: ASCII terms as quoted strings, non-ASCII terms as UTF-8 literals, because RFC 3501 quoted strings are 7-bit and GreenMail (and strict servers) misread 8-bit quoted strings; imapflow's `search()` cannot send literals, so `raw-uid-search.ts` sends the command through the client's `exec` (first ending an active IDLE with a NOOP, because `exec` skips imapflow's IDLE handling) and `search-response.ts` reads `SEARCH` and `ESEARCH ALL` answers: ranges from every untagged response are collected and `newest-uids.ts` expands only the newest 100 000 UIDs in linear time, whatever the wire order. A rejected search (`NO`/`BAD`, e.g. `BADCHARSET`) is retried once with ASCII-folded terms (NFD, combining marks removed) and otherwise answers `{uids: [], complete: false}`; a dropped connection is an error. GreenMail matches `FROM` against the address, not a substring of the display name.
- Gmail: OAuth 2 (desktop loopback + PKCE in local mode, server web flow in synced mode) then XOAUTH2 over IMAP/SMTP. Needs a Google Cloud OAuth client ID configured via env/settings.
- Outlook / Microsoft 365: same pattern, later.
- `SmtpMailSender` (nodemailer). `HttpsUnsubscribeSender` posts RFC 8058 one-click unsubscribes to public https URLs only: it resolves the host once, denies every non-global address (including IPv4 embedded in IPv6), pins the connection to the validated IP while keeping the Host header and SNI, and never follows redirects, from the desktop main process in local mode and from the server in synced mode, never from the renderer.
- `MimeParser` (mailparser). `ThreadBuilder` (Message-ID / References / In-Reply-To). `JiraClassifier` (sender + headers + subject patterns, outputs split + task events).
