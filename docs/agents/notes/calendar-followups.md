## 1. Durable invitation ingestion

- `MessageIngestor.create` queues a `calendar-invite` pending-work row (ref = message id) in the SAME transaction as the message (`CalendarPartsSink.queue`). Drafts and spam are ignored as before.
- `ChangeFlusher.flush` ends with `CalendarPartsSink.flush(userId, account)` -> `InviteWorkProcessor.processDue`: every due row is applied in its own unit of work (event upserts + removal of the row, revision-checked), so a crash at any point leaves the row and it is applied on the next flush. Re-applying is idempotent through SEQUENCE/DTSTAMP precedence.
- A failure rolls back that row's transaction only and reschedules it (`invite-retry.ts`: 1 min, 5 min, 30 min, 2 h, 12 h). After the sixth failed attempt the row keeps `failedAt` + `lastError` and is never retried; other rows and the message are never blocked. Retry state lives in the JSON payload, no schema change.
- One `calendar.updated` event per flush when any published row changed something.

## 2. Back-fill of invitations synced before the feature

- What is stored locally: message rows keep attachment metadata (content type, filename) but not the attachment bytes, and the raw MIME is not stored. So the parts must be fetched again, but only for candidate messages.
- Migrations `store-sqlite 0011_calendar_invite_backfill` and `server 0013_calendar_invite_backfill` insert one `calendar-backfill` pending-work row per existing mailbox (not drafts/spam) with `afterUid: 0`. New accounts never get rows, so nothing is re-fetched for them.
- `InviteBackfill` (runs in `AccountSynchronizer` after reconcile, before the final flush, on the already open provider session) reads the rows, lists candidates through `InviteCandidateRepository.listAfter(mailboxId, afterUid, limit)` (attachment content type `text/calendar`, `application/ics`, `application/x-ics` or a `.ics` filename, UID order), fetches each candidate with `fetchMessage`, queues its calendar parts as normal `calendar-invite` work and advances the cursor in the same transaction. Budget: `CalendarOptions.inviteBackfillBatch` messages per sync (default 50). The row is removed when a mailbox is exhausted, or when the mailbox no longer exists. A provider error pauses the back-fill (logged) and the next sync resumes from the cursor.

## 3. REPLY ordering and Sent copy

- A REPLY without a stored event (or instance) is parked as `calendar-reply` pending work keyed by uid + recurrence id + attendee (only the newest per SEQUENCE/DTSTAMP is kept). When a REQUEST stores that uid + recurrence id, the parked replies are applied in the same transaction (stale ones with a lower SEQUENCE are dropped). Parked replies older than 90 days are pruned at that point.
- `RsvpService` sets `In-Reply-To`/`References` to the invitation's Message-ID and records the sent REPLY through the compose `SentMessageRecorder` (Sent append + ingest, Gmail skipped as before, failures logged without failing the RSVP). The sent copy's own REPLY part goes through the normal queue and is idempotent.

## 4. MCP calendar tools

- `list_events` (`from` ISO with offset, default now; `days` 1-31, default 7; `limit` 1-200, default 50; cancelled occurrences skipped) and `get_thread_events` (`threadId`). Both read-only, results carry `timeZone`, the untrusted notice, and all times as wall time with offset in that zone (`presenters/zoned-time.ts`; all-day events as dates).
- `MailToolBackend.listEvents` / `getThreadEvents`, socket methods `listEvents` / `getThreadEvents` (zod params + results on both sides), `engineMailToolBackend(services, userId, timeZone: () => string)` now needs `calendar` in the services and a zone provider.
- Zones: desktop local runs use the device zone of the main process (`deviceTimeZone`). Server runs (also the device-held local CLI for synced jobs) use `input.timeZone` of the `chatAnswer` job, which the renderer now sends (`systemTimeZone()`); unknown zones are rejected with 400; other job kinds and old jobs fall back to `UTC`, stated in the result.
- Authorization: unchanged model. Server `/mcp` resolves the backend from the per-job token for `job.userId` only; both tools are read tools so `scopeMailToolsToJob` passes them for every job kind and still refuses writes for non-chat jobs. `@relay/ai` `MAIL_READ_TOOLS` includes both, the chat prompt mentions them.

## 5. RDATE PERIOD

- Flattening at parse time records each period's exact length as `X-RELAY-RDATE-DURATION:<recurrence key>|<ms>` in the stored ICS. The expander uses it for that occurrence's end, and the stored series range covers the longest period. The REPLY builder does not copy X- properties.

## 6. RECURRENCE-ID;RANGE=THISANDFUTURE

Branch `fix/bcc-and-series-cancel`.

Design: a series cut-off honoured by the expander, not a rewrite of the organizer's ICS. The stored ICS of every row stays exactly what the organizer sent (valid for REPLY building and later updates). Range changes and cuts live in their own rows, next to the exact instance rows.

- Row kinds (branch `fix/calendar-followups`): per series and recurrence id there are three slots. The occurrence row (no `thisAndFuture`) holds the exact instance (instance REQUEST or plain instance CANCEL). The range request record (`thisAndFuture`, no `endsSeries`) holds the newest range REQUEST at that recurrence id. The cut record (`thisAndFuture` + `endsSeries`, a cancelled THISANDFUTURE VEVENT) holds the newest cut there. Both stores key them by `recurrence_key` = the recurrence id, `<recurrence id>;RANGE=THISANDFUTURE` and `<recurrence id>;RANGE=THISANDFUTURE;CUT` (`calendarRecurrenceKey`, `sameSlot`, `rangeRecordAt`, `cutRecordAt`, `CUT_RECORD_SUFFIX` in `engine/services/calendar/recurrence-slot.ts`, exported for the stores, the memory repositories and the Google revision carry). So a cut never overwrites a range request at the same anchor, and that range comes back with its own data once the cut no longer applies. The unique index `(series_key, recurrence_key)` and every upsert target stay unchanged. Each row has one revision (its own SEQUENCE/DTSTAMP).
- Migrations: SQLite `0015_calendar_this_and_future` / Postgres `0017_calendar_this_and_future` added `this_and_future`, `ends_series`, `range_sequence`, `range_dtstamp`. SQLite `0016_calendar_range_records` / Postgres `0018_calendar_range_records` convert the old one-row model and drop `range_sequence`/`range_dtstamp`: every `this_and_future` row is re-keyed to the range slot; a range row whose anchor was cancelled on its own (cancelled, not a cut, master not cancelled) gets a cancelled occurrence copy (new random `cev_` id, the row revision, its ICS and message) and becomes a range record again (range revision, `REQUEST`, status `tentative` when its ICS has a `STATUS:TENTATIVE` line, else `confirmed`); a cut whose anchor was cancelled again on its own gets the same occurrence copy and its cut revision back. Range rows of a wholly cancelled series stay cancelled. The message/thread link of the original range REQUEST was already overwritten by the CANCEL before the migration, so converted range records point to the CANCEL message. SQLite `0017_calendar_cut_records` / Postgres `0019_calendar_cut_records` re-key every cut (`this_and_future` and `ends_series`) to the cut slot (data only, no schema change).
- Engine:
  - `InviteRequestHandler` looks up the row in the event's own slot and stores every REQUEST that supersedes that slot, so a plain REQUEST at a cut or at a range anchor only writes the occurrence row and a range request at a cut anchor only writes the range slot. REQUESTs older than a cut that applies at their recurrence id (out-of-order delivery, or a range request at the cut anchor that is not strictly newer) are stored as well, not dropped: the expander hides them while the cut applies and their cards show "cancelled", and they come back with their own data when a newer master supersedes the cut. Arrival order therefore never decides what is stored.
  - `InviteCancelHandler` (plain CANCEL): an instance CANCEL only touches the occurrence row; without one it stores an occurrence tombstone (also for an untimed CANCEL when a range record sits at that recurrence id). A whole-series CANCEL cancels only the master row (when one exists): overrides, range records and cuts keep their own data and revision, and the cancelled master hides every override older than it (expander `live-overrides.ts`, engine `effective-event.ts`). A newer master REQUEST restores the series and with it every override and range record with its own data; overrides the organizer cancelled on their own stay cancelled. A whole-series CANCEL of a series without a master row still cancels every non-cut row (there is no master to carry the cancellation).
  - `InviteRangeCancelHandler` (CANCEL with the flag): ignored when older than the master, than the cut at that recurrence id or than the range request at that recurrence id. Otherwise stores the cut in the cut slot from the CANCEL's own VEVENT (a bare CANCEL takes the title of the previous cut, the range request or the series) and cancels the master when the cut is at or before its start. It never rewrites occurrence rows or range requests: the expander hides them while the cut applies, a newer instance REQUEST at the cut restores that instance only, a newer range request that lifts the cut restores them under its own changes, and a newer master (which makes the cut obsolete) restores them with their own data. Their thread cards still show "cancelled" and RSVP to them is refused: `effective-event.ts` derives the status from the cuts applying to the row (a range request with the same revision as a cut at its own anchor counts as cut off, like in the expander) and from a cancelled master newer than the row, and is used by `InvitationQuery`, `RsvpService` and `GoogleFirstRsvpService` before any reply is built, mailed or sent to Google. Replays with the same SEQUENCE/DTSTAMP write nothing.
  - REPLY handling and parked replies match the slot too (`CalendarReplyWork.thisAndFuture`), so a REPLY to a range request never lands on the anchor instance; `InviteResponses` and subscription feeds (`feed-events.ts`) key by slot as well.
  - `SeriesRangeKeeper` recomputes the master's `rangeEndsAt` through `seriesRangeEnd` after every invite write that touches a series with THISANDFUTURE rows and saves it with `saveIfCurrent`, inside the same retried unit of work (also on replays). Range request records get the same range end (`series-range-rows.ts`). `listForRange` therefore stops returning a cut series after the cut. Feed refreshes do the same per feed (`feed-series-ranges.ts`).
  - `InvitationTimingResolver`: the card of a range request record expands the whole series and shows the first non-cancelled occurrence driven by that record, so the anchor while it stands and the next derived occurrence when the anchor alone is cancelled or changed by its own instance REQUEST. It searches successive 400-day windows (at most ten) from the anchor, so sparse series (for example every second year) find the next one too. Without a master row, when nothing is found or when the record is effectively cancelled it shows the record's own time.
- Expander (`expand/series-plan.ts`, `series-choice.ts`, `range-span.ts`, `kind-change-span.ts`, `exact-rows.ts`, `live-overrides.ts`, `series-membership.ts`):
  - Live overrides: cuts older than the master are dropped before anything else (also as the exact row at their own anchor), and when the master is cancelled every override older than it is dropped. `seriesRangeEnd` uses the same rows.
  - Exact rows: per recurrence id the newest of the occurrence row, the cut and the range request is the exact override (ties: occurrence row, then cut, then range request, `exact-rows.ts`). So a newer instance at a cut or at a range anchor is shown, an older one is replaced by the cut (shown as the cancelled anchor) or by the range record (shown with the range change); the range record drives the later occurrences either way.
  - Cut: a cut whose SEQUENCE/DTSTAMP is not older than the master ends the series. No occurrence at or after its recurrence id is produced (RRULE with COUNT or UNTIL, RDATE incl. flattened PERIOD lengths, EXDATE all go through the same iterator), and overrides at or after it that are older than any cut applying at their recurrence id are hidden (several cuts can apply at once; the newest decides). Overrides newer than the cut (the organizer sent the instance again, also exactly at the cut) stay. A cut older than the master is ignored, like an old instance CANCEL. A cut at or before DTSTART leaves nothing. A range request anchored at or after a cut with a strictly newer SEQUENCE/DTSTAMP lifts it: occurrences come back from its anchor on with its changes, the ones between the cut and that anchor stay cancelled, and a later newer cut ends the series again. A range request anchored at or before a cut never extends past it, whatever its revision (a not-older cut at its own anchor ends it there). The expander decides every occurrence by these segments (`series-choice.ts`) and only stops iterating at the first cut that nothing lifts.
  - Range REQUEST: from the record's recurrence id on, every master occurrence gets the record's time shift (measured and applied in wall time of the master zone, so it is right on both sides of a DST change and for changes made across one), its duration and all its properties (the occurrence's `event` is the range record, `recurrenceId` the original instance key). When only its anchor is cancelled (plain instance CANCEL, an occurrence row), the anchor stays cancelled and the later occurrences keep the change with the record's own status, so they can be answered: the RSVP goes to the range record and the REPLY carries `RECURRENCE-ID;RANGE=THISANDFUTURE` with the record's SEQUENCE. Among several range records the newest (SEQUENCE, DTSTAMP, then the later one) wins. An exact override, cancelled or not, wins only when it is not older than the range record; older exact overrides (also older instance cancellations) are replaced, newer ones stay. A nominal DURATION of the range request (for example `P1D`) is applied in wall time per occurrence, an exact DTEND length as elapsed time. Expansion widens its iteration by the largest shift so occurrences shifted into a window from far outside it are found.
  - All-day kind change (`kind-change-span.ts`): the day shift is the number of calendar days between the anchor date and the occurrence date, both in the master's wall clock (date and floating keys as written, UTC keys and timed occurrences converted to the master zone), applied to the range record's own DTSTART. Timed master -> all-day range: later occurrences become all-day on their date in the master zone plus that shift, with the range's nominal length in days, shown like every all-day event in the viewer zone. All-day master -> timed range: later occurrences get the range's wall time in the range's own zone (TZID, UTC or floating in the viewer zone) on the shifted date, so DST is applied per occurrence; the length is the range's DURATION in wall time or its exact DTEND length. Mixed-kind ranges widen the expansion reach by a day instead of an hour.
  - Shortened series (`series-membership.ts`): an override (also a range record's anchor row) that is older than the master and whose recurrence id is no longer an occurrence of the master (RRULE/COUNT/UNTIL shortened, also EXDATE or a moved DTSTART) is hidden. Overrides not older than the master (sent together with it or re-sent after it) stay. The check runs only for leftover overrides that overlap the window, iterating the master from just before the recurrence id; on an iteration error or when the iteration limit (`MAX_ITERATIONS`, COUNT rules are not fast-forwarded) runs out before the recurrence id, membership is unknown and the override stays. The Google Calendar API path goes through the same expander (rows carry Google's `sequence` and `updated` as revision).
  - Recurrence ids are compared as instants: UTC keys directly, date and floating keys in the viewer zone (`recurrence-instant.ts`).
  - The parsed ICS cache is keyed by the ICS text. It was keyed by id + `updatedAt` + ICS length and returned the old RRULE when a master was stored twice in the same flush with an ICS of equal length (for example `COUNT=10` -> `COUNT=12`).
- `CalendarExpander.seriesRangeEnd(master, overrides)` (port method): the stored range end of a master with its cut and shifts, `min(natural series end, cut + longest occurrence + 1 day)` where the longest occurrence includes RDATE periods and range shifts. Fake expanders return `master.rangeEndsAt`.
- Google Calendar API path: Google events carry no RANGE (RECURRENCE-ID comes from `originalStartTime`), Google sends a new REQUEST with a shortened RRULE for "this and following", which is a normal master update; exceptions after the new end are hidden by the shortened-series rule. The Google upserts copy the row columns and carry revisions by the same recurrence key.

- Arrival order: `InviteQueue` gives queued `calendar-invite` work strictly increasing `createdAt` values, so messages synced in the same millisecond are applied in arrival order. Before, ties fell back to the message id, whose random suffix shuffled them; a plain instance CANCEL could then be applied before its REQUEST and get lost.
- E2E tests wait until every message is synced (one thread per message) and the `calendar-invite` queue is empty before asserting (`apps/server/test/calendar/support/invite-settle.ts`); the desktop test checks that every SMTP delivery is in INBOX first and that the queue is empty after `local.sync.now`.

Remaining gaps:

- REPLYs to a range parked before the upgrade carry no `thisAndFuture` flag (the old payload never stored it), so after the upgrade they are matched as replies to the anchor instance.
- Invitations ingested before the migration are not re-evaluated (a THISANDFUTURE CANCEL ingested earlier stays single-instance until it is ingested again).
- Rows a whole-series CANCEL cancelled before this change, and range requests a cut overwrote before the cut-records migration, keep the CANCEL's revision or are gone; a newer master does not bring them back (their own revision and data were overwritten).
- A whole-series CANCEL of a series known only from instance invitations (no master row) still cancels those rows; a master sent later does not bring them back.
- SEQUENCE is per component, but master and overrides are compared by SEQUENCE first: an override with a higher SEQUENCE than the shortened or cancelled master (an instance edited more often than the series, common with Google) counts as newer and stays visible even when its DTSTAMP/`updated` is older.
- The thread card of an override hidden because it is no longer an occurrence of a shortened master still shows it as answerable: the engine does not evaluate RRULE membership, only the calendar view hides it.
- Pre-existing, found while writing the e2e tests: a plain instance CANCEL without DTSTART for an instance that has no row yet (and no range record at that recurrence id) is ignored, so that instance stays visible.

## gpt-6.1-sol review (4 findings, all fixed)

1. Retry scheduling overwrote a newer re-queue and could mark it failed: new revision-checked `PendingWorkRepository.replace(work, payload)` (memory, SQLite, Postgres); a stale reschedule is a no-op.
2. Replayed (back-fill) or reordered REPLYs could overwrite a newer response: `CalendarAttendee.repliedAt` (optional, stored in the attendees JSON) records the DTSTAMP of the applied REPLY, older REPLYs of the same SEQUENCE are ignored; a local RSVP records `repliedAt = now`.
3. Replaying an identical REQUEST (same SEQUENCE, DTSTAMP and status) reset attendee responses: it is now a no-op that still releases parked replies.
4. Zoned RDATE PERIOD lengths across DST were measured in wall time: endpoints are resolved to instants with the RDATE TZID, duration-form periods use their duration.

No issue found by the reviewer in: atomic message/work insertion, poison isolation, back-fill transaction boundaries and SQL predicates, migration seeding, MCP user scoping and job-kind write refusal, socket validation, zone propagation and formatting.

## Notes for other agents

- Anyone constructing `Repositories` must add `inviteCandidates` (memory, SQLite and Postgres implementations exist).
- Anyone implementing `PendingWorkRepository` must add `replace`.
- google-calendar: `google-first-rsvp.ts` does not set `repliedAt` on the attendee yet; set it to the RSVP time so a replayed older REPLY cannot undo a Google-side RSVP.
- `createCalendarComponents(deps, events, sentCopies, ...)` returns `CalendarService` directly; invite ingestion lives in `createInviteComponents(deps, events)`.
